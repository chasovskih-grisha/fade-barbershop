- **2026-10-09 (T-046: «Записати» з картки клієнта — і розсинхрон id у сусідній таблиці)** — закрито перший пункт Done задачі: дія «Записати» зʼявилась **на картці клієнта** (§6.2 «Дії»: «Записати» — створення візиту для клієнта, шлях до `booking-flow`), а не лише в рядку списку, як у зрізі 2026-10-06. `ClientHeader` отримав слот `actions` (той самий патерн, що в `PageHeader`), сторінка `/clients/[id]` передає туди кнопку; навігацію тримає сторінка — заголовок лишається презентаційним. **Найдорожча знахідка — не в новій кнопці, а поруч із нею:** таблиця списку вела на `/bookings/phone?clientId=<ClientProfile.id>`, тоді як контракт телефонного запису — **`User.id`**: preselect-крок резолвить картку через `GET /admin/clients/by-user/:userId` і пише той самий id в `origin.clientId`, а читачі візитів (`list-client-appointments`, `own-appointment`) шукають записи за `clientId = userId`. Для реальних клієнтів `ClientProfile.id` — окремий uuid (`@default(uuid())`, `createClientProfile` → `ids.id()`), тож візит, створений зі списку, був би **невидимим у кабінеті клієнта** (та сама тиха втрата, що описана 2026-10-02, тільки з іншого входу); маскував баг **сід**, який свідомо пише `ClientProfile.id = userId` (`seed-customers.ts`) — у dev-даних обидва id збігаються, тому розбіжність не кидалась в очі. Обидва входи тепер будують шлях однією функцією `phone-booking-path.ts` — контракт в одному місці, як `phone-test-helpers` для форми. **Покриття:** `[id]/page.book.test.tsx` (4 — дія веде на запис із `clientId = userId`; картку читає за профільним id, а запис веде за `userId`; клієнт без імені й VIP — дія доступна; помилка завантаження — банер і жодної дії) + `ClientsTable.test.tsx` (фікстури навмисно з `id ≠ userId`, інакше регресія непомітна). **Обидва тести доведено навантаженими:** повернення багу (`client.id` замість `client.userId`) фарбує рівно id-твердження в обох сюїтах (2+2), після відкату — зелені. Гейти: admin **120/120** (38 suites), tsc/eslint/prettier на змінених файлах чисті, всі змінені файли < 100 рядків (LOC-гейт ADR 0019). **Лишається відкритим у T-046:** депозит-посилання (SMS/push) або позначка «оплатить на місці» — платіжний контур фази 8 (T-091/T-093); «Додати до черги» (WTL-ADM-02, фаза 17) і «Написати» (чат, фаза 7) з того ж блоку «Дії» — свої задачі. - **2026-10-05 (dev-стек: гаряче перезавантаження API більше не обслуговує застарілий бандл)** — закрито знахідку з T-043 (2026-10-02): «контейнер API з `nest start --watch --webpack` пережив невдалу перезавантажу — процес лишився живим зі старим бандлом `dist/main`». **Причина — не в Docker і не в монтуванні, а в `WebpackCompiler` Nest:** restart-hook викликається лише коли `!stats.hasErrors()`, а на невдалій перебудові webpack нічого не емітить — тож старий бандл лишається і процес його обслуговує; `deleteOutDir: true` видаляє `dist/` лише раз, на старті watcher. **Лікування не патчить Nest:** `apps/api/webpack.config.js` (лише додає плагін до власного `webpackDefaultsFactory`) пише `dist/.build-status.json` на кожній завершеній збірці, а `apps/api/scripts/dev-watch.mjs` володіє обома половинами — builder `nest build --watch --webpack` і сервер `node --enable-source-maps dist/main.js`: на невдалій збірці **гасить** сервер, і (пере)запускає лише після успішної. Compose-команда api викликає супервізор напряму (package.json в образі не монтується, тож `pnpm dev` в контейнері читав би стару команду), а `scripts/` і `webpack.config.js` додані в bind-mount. **Найдорожча знайдена пастка:** наївний сигнал по `stats.hasErrors()` **бреше в watch-режимі** — Nest тримає ts-loader у `transpileOnly: true` і делегує типи `ForkTsCheckerWebpackPlugin`, чий `done`-tap асинхронний: бандл збирається й `done` вже спрацював, а тип-чек приходить пізніше, тож перша версія плагіна писала `ok:true` для коду, який не типізується (а рестарт навіть переносився б на свіжий бандл). Виправлено переходом на власний хук плагіна `issues` (там відома й кількість bundle-помилок із `compilation.errors`); фолбек на `done`/`stats` лишається для випадку без ForkTsChecker. **Жива перевірка в контейнері (обидва класи відмов):** тимчасова TS-помилка в `app.module.ts` → `build FAILED (1 error) → api server stopped`, `curl /health` = **000**, статус `{ok:false,source:"issues"}`, контейнер **Up**; неіснуючий імпорт (bundle-помилка) → те саме; повернення коду → `build ok → restarted`, `/health` = 200. Гарантія: поки білд у процесі — обслуговується останній успішний бандл (як звичайний hot-reload), щойно збірка падає — сервер не працює (fail-closed), після виправлення піднімається сам. **Прод не зачіплено:** `nest build` використовує tsc і цей webpack-конфіг не читає. Покриття: `node --test` на чистій таблиці рішень `scripts/dev-watch-lib.mjs` (**7/7**, у т.ч. інваріант «невдала збірка ніколи не (пере)запускає сервер»); `test:dev-watch` у скриптах api. Оновлено: ADR 0018 §5, коментар сервісу api в `infra/docker-compose.yml`. **Свідома межа:** супервізор гасить сервер лише коли про провал **стало відомо** (після завершення збірки) — під час самої збірки обслуговується останній успішний бандл, інакше кожна правка давала б простій.

- **2026-10-03 (T-080: нагадування про візит — SMS-контур нагадувань; розбіжність у назві задачі)** — запит був «реалізувати споживача нагадування (T-080) за патерном T-4608». **Перший крок — не писати код, а звірити задачу з платформою:** T-080 називається «Контекст `notifications`: **push-канал**», а «нагадування» є лише одним пунктом у переліку подій; патерн, який T-4608 називає «перевіреним для нагадувань (T-080)», **не мав власної задачі взагалі**. Push при цьому не «дорогий», а **неможливий**: у схемі немає `DeviceToken`/`DeviceRegistration`, немає `PushGateway`/Expo — це окрема робота. Тому зроблено те, що замовили по суті, а розбіжність явно зафіксовано у файлі задачі. **Рішення (запитав у користувача, не вигадував):** три розвилки — (1) таймер у памʼяті vs подія в outbox із часом спрацювання → **подія** (переживає рестарт, узгоджується з T-042c), (2) канал → **SMS** клієнту (push недоступний), (3) відписка → **операторський тумблер** у налаштуваннях (персональної колонки в `ClientProfile` немає; тихих годин свідомо не робили).
  - **Схема:** `OutboxMessage.availableAt DateTime?` + індекс `(type, publishedAt, availableAt)`; `NULL` = «доставти негайно», тож семантика T-4608/T-4422 не змінилась. Окремої таблиці «розкладу» не заводив — вона дублювала б `OutboxMessage` без додаткової цінності.
  - **Головна знахідка (це зламало б контур навіть із правильними тестами):** `NotificationRecord.eventId` **унікальний**, а подію візиту тепер читають **два** споживачі (підтвердження й планувальник). Без іменованого ключа планувальник або побачив би запис підтвердження → «дубль» → нагадування не планується **ніколи**, або впав би на унікальному індексі. Ключ став `<eventId>:reminder-schedule`, регресія закрита юнітом. Це не «дрібниця», а наслідок самої зміни моделі (один тип події → кілька споживачів) — варто памʼятати для будь-якого наступного споживача outbox.
  - **Релей узагальнено:** `infrastructure/outbox-routing.ts` мапить тип події на **список** споживачів; рядок закривається `publishedAt` лише коли всі довели справу (handled/duplicate), `ignored` лишає pending. Вибірка враховує дозрілість: `OR: [{ availableAt: null }, { availableAt: { lte: now } }]`. Падіння send **не** журналюється — рядок лишається pending (at-least-once).
  - **Перенесення візиту** не залишило б старе нагадування: `rescheduled` скасовує ще не спрацьовані рядки (`status='cancelled'` + `publishedAt`) і планує нове на `newStart`.
  - **LOC-гейт (ADR 0019) змусив розкласти навіть дрібні шматки:** провайдери винесено в `notifications.providers.ts` + `appointment-reminder.providers.ts` + `relay.providers.ts`, обробку одного рядка — в `outbox-handle.ts`, фейси — у `fakes` + `events`, а `outbox-dispatcher.spec.ts` (120 рядків) розділено на таймер і `outbox-relay.spec.ts`. `notifications.module.ts` знову декларація, а не список на 140 рядків.
  - **Тести:** юніт 25 (фільтрація/дублі/відписка/захисні умови/ретрай/текст/налаштування) + регресія на ключ журналу + wiring-модуля; e2e на Postgres **3** (`barbershop_e2e`): рядок події → план із `availableAt = start − leadMinutes` → повторний прохід не дублює → спрацьований рядок закривається (канал `none`, без SMS) → перенесення скасовує старе й планує нове. Для e2e довелося застосувати міграцію до e2e-БД (`pnpm e2e:db:prepare`) — інакше перший прогін падав на `column "OutboxMessage.availableAt" does not exist`; це ж показало, що **без `DATABASE_URL` у середовищі `jest.setup.js` не перемикає базу** і сюїта пішла б у dev-БД (той самий ризик, що вже описаний 2026-10-02).
  - **Гейти:** api unit **818/818** (181 suite), e2e **81/82** — падає лише `fresh-bootstrap` (Compose v5.4.0 не підтримує `--profile`, екологічне, зафіксовано раніше), typecheck 11/11, lint 0 errors, prettier і `docs:validate` зелені. Міграцію застосовано і до dev-БД (`migrate deploy`), щоб локальний стек не падав на новому рядку.
  - **Лишається відкритим у T-080:** сам **push** (модель `DeviceRegistration`, `PushGateway`, ротація токенів, тихі години) — це справжня решта задачі, SMS-контур її не закриває. Також персональна відписка клієнта й реальний SMS-провайдер у проді (у dev — Mailpit «SMS як email»). — запит був «полагодити `nearest-locations-fallbacks`, `admin-availability` (socket hang up), `admin-account` (404)». **Спершу не повірив власній діагностиці:** жоден з трьох не відтворився ані сам по собі (`admin-account-active` — **30/30 зелених**), ані на `--maxWorkers=100%`. Ротаційний флейк не має «свого» теста — він **проявляється тим тестом, який випадково дістав «заражений» воркер**. Тому фіксирував підписи, а не імена сюїт, і дав 20 прогонів: підтвердилися саме ті, що їх назвали, плюс `SetAppointmentReference`/`Booking flow GWT`.

Токен тепер `randomUUID()` на прогін; у `web-client.fixture` зафіксовано контракт. **Це головна знахідка:** фікстура, яка виглядає «своєю», робить сусідні сюїти залежними від порядку.
  - **Причина 2 — `afterAll` маскував `beforeAll`.** `afterAll(() => ctx.cleanup())` падав із `Cannot read properties of undefined (reading 'cleanup')`, тож у лозі було «Test suite failed to run» і **не було видно справжньої помилки** bootstrap; гірше — частковий стенд (Nest app + пул Prisma) лишався відкритим у воркері, звідки `socket hang up` у наступних сюїт. `lifecycleSuite` тепер обгорнуто в `try/catch`: закриває підняте й **повторно кидає** оригінал, а `cleanup` — замикач, безпечний до виклику.

Замінено на `CrmModule + IdentityModule` (остання — заради глобального `AdminSessionGuard`, а не репозиторіїв).
