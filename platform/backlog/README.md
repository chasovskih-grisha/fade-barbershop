# Backlog — глобальний роадмап і задачі

> **Одна задача = один файл** `tasks/T-NNN-*.md`. Статуси — у `index/`, один файл на етап. Журнал уточнень — у `journal/YYYY-MM.md`. Цей README — карта: етапи, пріоритет, залежності, ризики. Він не росте разом із задачами.
>
> Вимоги зібрані з `docs/acceptance-criteria/`, `docs/roadmap.md`, `docs/booking-flow.md`, екранних специфікацій, README контекстів API і ADR. Кожен файл задачі вказує свої джерела.
>
> Правило гейтів: фаза закривається, коли всі її задачі `done` **і** критерії її AC-груп мають статус «прийнято» у `docs/acceptance-criteria/traceability.md`. Порядок всередині фази не жорсткий, залежності вказані в кожній задачі.
>
> Статус на **2026-11-18**: 805 задач в індексі (558 топ-рівневі задачі + 247 слайсів) — **4 551 SP** загалом; статуси: 541 `todo`, 96 `in_progress`, 89 `review`, 73 `done`, 3 `split`. Сума етапів: **4 551 SP**.

## Як користуватись

- **Теги задач**: `backend`, `frontend`, `infra`, `devops`, `integration`, `high-risk`, `experimental`
- **Складність**: `junior`, `middle`, `senior` — для планування розподілу команди
- **Статуси** ведуться у `index/`, не у файлах задач і не в цьому README. Файл задачі — специфікація «що і чому».
- **Нова задача** = файл у `tasks/` + рядок у `index/` свого етапу. Задача без AC/джерела не береться.
- **Журнал**: новий запис додається в `journal/` за поточний місяць. Минулі місяці не переписуються.
- **Покриття компонентів**: новий каталог у `apps/`/`packages/`/`apps/api/src/` → рядок у `coverage-matrix.md` + задача в індексі одним комітом; компонент без задачі там одразу видно.
- **Definition of Done запуску**: чеклист v1 з roadmap змаплено на задачі-власники у `definition-of-done.md` — запуск = усі пункти закриті (задача `done` + чекбокс roadmap); зміна чеклиста → правка обох файлів одним комітом.

## Етапи (Milestones)

### M0 — Фундамент — фаза 0
Монорепо, інфраструктура, CI. *Без цього не починається нічого.*

### M1 — Ядро сервісу — фази 1–4, 10A паралельно
Identity, адмін-каркас + дані, сайт/кабінет, scheduling з референсом і партіями. *Тут система вже може вести календар.*

### M2 — Гроші і люди — фази 5–8, 10B
CRM, mobile, барбер mobile, messaging, **billing з ПРРО**. *Тут можна реально приймати клієнтів.*

### M3 — Запуск v1 — фази 14, 15, 23, операційна підготовка
Аналітика (жорстка вимога), walk-in, живі слоти, дані і фіскалізація CLT-01, тест-прохід. *Відкриття.*

### M4 — Контур утримання і розум — фази 11–13 (слайси, якщо не увійшли в v1) + 16–22
Лояльність, відгуки, знижки, no-show, waitlist, win-back, галерея, сертифікати, рефералка, self-service графік. *Захист слотів і повернення клієнтів; AI-трек (10A) — сюди, якщо зсунулися з M1/M2.*

### M5 — Публічність і магазин — фази 23–27
Публічні відгуки, SEO-сторінки, shop-lite → повний магазин. *Зростання поверх працюючого ядра.*

### M10 — Мережа (за бізнес-тригером) — фаза 9
Друга локація: дані, ціни по локації, override політики депозита, роль `location_manager`. *Старт — після підписання другої точки, не за календарем; порядок задач встановлює T-302.*

### M7 — Асистенти (за рішенням засновника, після M4/M5) — фаза 28
Контекст `assistants`: оркестратор, ConciergeAgent для клієнта, OwnerAnalystAgent для засновника, OpsAgent для барбера. *Шар над готовим ядром — потребує канали (фаза 7) і дані (фази 4–5, 11–14). Позиція в роадмапі: `docs/roadmap.md` фаза 28; підсвітка «чому тут» — ADR 0020.*

## Пріоритет і правило відрізання

- **Найвищий пріоритет — знак FADE.** [T-4609](tasks/T-4609-location-logo.md) і слайси a–d беруться першими, до прод-гейту і до решти M1–M3. Порядок усередині: **a** (лишився `exports` пакета; модель і секція локації вже в дереві) → **b, c, d паралельно** (сайт, адмінка, застосунок). Нічний хром: `lockup-on-dark.svg`, вузький знак `mark-fa-on-dark.svg`, вкладка `favicon.svg`. Одразу після хрому, теж до прод-гейту — лист: [T-4611](tasks/T-4611-email-template-design-system.md) a → b (`emailLogo` = `lockup-on-milk.svg`) → c.
- **Далі прод-гейт — [T-4614](tasks/T-4614-preopening-production-mvp.md)** і слайси a–f. Кожен слайс — один блокер: прод-образи (a), база без демо-сіду (b), автодеплой, який зараз виходить 0 (c), cookie `.fade.com.ua` на стейджі (d), вітрина «Записатися» при нулі локацій (e), адмінка на порожній базі (f). Інфра стенда — T-303 і T-4531. Вітрина (e) сідає на шапку вже зі знаком (T-4609b), не на слово «Fade».
- Порядок етапів жорсткий: **M0 → M1 → M2 → M3** — шлях до запуску; M4/M5 — після запуску за даними дашборда (T-302).
- **M7 (асистенти, фаза 28)** — після M4/M5 за окремим рішенням засновника: шар читає/викликає готові use cases і потребує дані (фази 4–5, 11–14) і канали messaging (фаза 7); LLM-провайдер і бюджет токенів — відкрите рішення (ADR 0020, ASSIST-відкрите #1).
- Фаза 10A (AI) — паралельний трек M1/M2: якщо тисне час — T-050…T-052 зсуваються після M3 (рішення засновника, fallback зафіксований в roadmap).
- Слайси 11A/12A/13B у v1 — окреме рішення засновника (чеклист запуску); задачі T-140…T-152 мають внутрішні чекбокси-слайси.
- Кожна задача посилається на AC-гейт: «done» = тест-прохід за GWT-сценаріями, де вони існують.

## Definition of Ready (задача береться в роботу, коли)

- Вимоги зафіксовані: AC-критерії існують, екран специфікований (якщо задача екранна), рішення-ADR прийняті.
- Залежності `done` або явно дозволені паралельно; AC-гейт відомий (що саме приймаємо).
- Немає відкритих питань, які блокують реалізацію (відкриті питання AC — або вирішені засновником, або мають v1-дефолт у критерії).
- Задача має чіткі Done-критерії з метриками успіху.
