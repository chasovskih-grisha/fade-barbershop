# T-4605 · Перейменування DTO на Request/Response/Payload (19/19)

- **Stage**: M6 (phase 40) · **Tags**: backend, frontend, architecture, quality · **Complexity**: senior · **Depends on**: T-2500
- **StoryPoints**: 19

## What

Глобальна заміна суфікса `Dto` на суфікси, які кажуть про **роль типу в потоці даних**, замість того щоб просто називати його «об'єктом передачі даних»:

| Суфікс | Коли | Приклад |
|--------|-------|---------|
| `*Request` | те, що **входить** у API (body, query, path) | `CreateLocationRequest`, `BookSlotRequest` |
| `*Response` | те, що **виходить** з API | `LocationResponse`, `AvailableSlotResponse` |
| `*Payload` | те, що **не HTTP-межа**: черга, outbox-доставка, webhook зовнішньої системи, тіло запиту до провайдера (SMS/ПРРО/еквайринг), аргументи MCP-інструментів | `AppointmentCommandPayload`, `PrroCheckoutPayload` |

Перейменовуються **файли, типи, Tests, імпорти, мапери й Documentation** — у всьому monorepo: `apps/api` (11 файлів, 27 декларацій), `apps/web` (9 типів), `packages/contracts` (`*Input`/`*Result` → `*Request`/`*Response`), `apps/admin`, `apps/mobile`. Глобально, не по контекстах «де встигли» — інакше в коді одночасно живуть три різні конвенції імені.

## Why

`Dto` — порожнє слово: воно не каже, **з боку** прийшли дані, **кому** і **в якому напрямку** рухаються. Наслідки:

- `CreateLocationDto` і `LocationDto` в одному файлі — різні речі (запит і відповідь), назви не відрізняються роллю.
- `CommandDto` (scheduling) — найменш інформативний ідентифікатор у кодовій базі: не видно, чи це HTTP-тіло, чи внутрішня команда.
- `NearestLocationsResponseDto` уже містить слово `Response` усередині — суфікс `Dto` не несе жодної інформації, лише шум.
- Другий конкуруючий словник у тому самому monorepo: `packages/contracts` послуговується `*Input`/`*Result`, `apps/web` — `*Dto`, `apps/web/src/lib/api/locations.ts` — взагалі без суфікса (`Location`, `Channel`, `Photo`). Три конвенції на одну відповідь API.

Мета — одна конвенція, яка читається без відкриття файлу, і два гейти, які не дадуть їй розтектися знову: лінтер (T-4605d) і специфікації (T-4605e).

**Разом по коду: 29 унікальних імен / 38 декларацій.** Жодного `class *Dto` — NestJS-декораторів валідації в API none (`class-validator` не в стекі), тож перейменування не зачіпає wire-контракт: імена TS-інтерфейсів стираються під час компіляції, міграцій DB і back-compat Shim не потрібно. Декораторів `@nestjs/swagger` в коді також none (пакет є в root-залежностях) — якщо їх додадуть, імена схем підуть від інтерфейсів, тому порядок «спершу перейменування, потім декоратори» має зберегтися.

## Дві речі, які треба закрити до механіки

Обидві — не «уточнення», а умова, за якої Epic можна вважати виконаним. Деталі й рішення — у відповідних слайсах.

**1. Колізія суфікса на `SlotRequestDto`.** `SlotRequestDto` (GET /slots, query) за механічним правилом дав би `SlotRequestRequest` — це не назва, це тавтологія, яка нікому не читається. **Пропозиція T-4605a: `SlotQueryRequest`** (дієсловно, як `Create*`/`Update*`/`Set*`). Правило має бути зафіксоване в ADR T-4605a **до** того, як хтось почне перейменовувати, інакше перший же файл закріпить тавтологію.

**2. none `class-validator`, none `class *Dto`, none декораторів `@nestjs/swagger` — але є дві однакові пари імен.** Перейменування **не** зачіпає wire-контракт (імена TS-інтерфейсів стираються компілятором, міграцій DB не потрібно). Але два контексти мають **однойменні** `LocationDto` / `BarberDto` / `ServiceDto` / `AvailableSlotDto` (див. інвентар), які після перейменування стануть `LocationResponse` / `BarberResponse` / `ServiceResponse` / `AvailableSlotResponse`. Ризик не в самій назві, а в тому, що вони живуть у різних контекстах і реекспортуються через barrel-файли: після перейменування два різні типи можуть опинитися в одному експорті. **Обов'язкова перевірка в T-4605b до Done**: чи не зливаються дублікати в barrel-експортах і чи не стає неоднозначним імпорт через `index.ts` контекстів.

## Відкриті питання (закриваються в T-4605a, до механічного перейменування)

1. **Колізія суфіксу.** `SlotRequestDto` (GET /slots, query) за механічним правилом дав би `SlotRequestRequest`. Пропозиція: `SlotQueryRequest` (дієсловно, як `Create*`/`Update*`/`Set*`).
2. **Вкладені типи в конверті.** `NearestLocationDto` (елемент списку) усередині `NearestLocationsResponseDto`. Пропозиція: елемент лишається суфіксованим — `NearestLocationResponse`; голий `NearestLocation` зіткнеться з доменним `Location` і з `LocationChannel`/`LocationPhoto` у вебі.
3. **`packages/contracts`.** «Вирівняти весь кодобейз» означає перейменувати й `*Input`/`*Result` — але це ламає 8 файлів-споживачів (`@fade/contracts` імпортують admin blog + 4 identity-контролери). Пропозиція: перейменувати в межах одного PR епіка, разом зі споживачами; окремий «совмісний» stage не потрібен — внутрішня контрактна бібліотека без зовнішніх публікацій.
4. **`*ErrorBody`.** `ContentErrorBody` / `IdentityErrorBody` — це теж відповідь API. Пропозиція: `ContentErrorResponse` / `IdentityErrorResponse`.
5. **Папка `dto/`.** Варіанти: (а) залишити папку, перейменувати лише файли; (б) `dto/` → `api/`, і заодно винести 16 інлайнових декларацій з контролерів — вони реально допомагають гейту `max-lines ≤ 100`; (в) розкидати по контролерах. Пропозиція: (б), але винесення інлайнових типів — окремий Slice, щоб не мішати з механічним перейменуванням. **Якщо (б) — обов'язковий amend ADR 0019**: він прописує «контролер окремо, DTO/validators/маппери — сусідні файли», тобто після перейменування папки ухвалене рішення стане хибним (розбір у T-4605e).
6. **`*Payload` ще порожня категорія.** Її треба **завести**, інакше третій суфікс — мертвий: перші справжні `*Payload` з'являться в T-3102 (webhook), T-3100 (черга сповіщень), T-092/T-093 (тіло ПРРО/еквайрингу), T-050 (AI-порція), T-2001 (MCP-інструменти). Пропозиція: зафіксувати межу — `Payload` = лише не-HTTP-межа; доменні події outbox лишаються подіями і не перейменовуються.
