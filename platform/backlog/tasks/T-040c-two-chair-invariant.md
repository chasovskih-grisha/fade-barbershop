## Поточний зріз (2026-09-25)

Механізм — **serializable-транзакція Prisma** (`isolationLevel: 'Serializable'`) навколо читання зайнятості й вставки: читання активних крісел + перетинів → перевірка `hasChairCapacity` (sweep-line у домені) → перевірка конфлікту барбера → insert. Конфлікт ізоляції `P2034` мапиться в `BookingConflictError` → HTTP 409 «оновіть слоти і повторіть» — ретраїть клієнт, сервер не ретраїть автоматично. Зафіксовано в `apps/api/src/scheduling/README.md` (розділ «Конкурентність і інваріант крісел»).

Race-Tests зелені проти Postgres: (1) соло-букінг — два одночасні запити за останнє крісло, проходить рівно один (`scheduling/e2e/admin-bookings.e2e.spec.ts`); (2) партія — атомарність ніг: конфлікт будь-якої ноги відкочує `AppointmentParty` + обидві ноги, нічого не лишається в DB; parallel не проходить поріг активних крісел; два одночасні sequential-партії за останню крісло → 201 + 409 (`appointment-party/e2e/appointment-party-race.e2e.spec.ts`). Продуктивність: юніт-benchmark валідатора (`scripts/benchmark-scheduling.ts`, 500 графіків за одиниці мілісекунд) + слот-агрегат 5 барберів 10.2–84.8 мс на локальному Docker API (замір з T-040) — гейт < 200 мс тримається.
