# T-4533 · Перенос запису зі збереженням зв’язків та історії

- **Stage**: M1 (phase 4) · **Tags**: backend, frontend, integration, high-risk · **Complexity**: senior · **Depends on**: T-040, T-042, T-045
- **StoryPoints**: 8

## What

Єдиний use case `RescheduleAppointment` для перенесення існуючого запису на іншу дату й час без створення нового запису:

- Клієнт переносить власний запис із кабінету, адмін — із картки/календаря; drag&drop T-4524a використовує той самий use case, а не окрему бізнес-логіку.
- Змінюються лише `startAt`/`endAt` та дані розподілу нового слота. `appointmentId`, клієнт, барбер, локація, послуга/позиції, `AgreedPrice`/`FinalPrice`, референс, коментар, статус, оплата, час створення та зв’язані записи залишаються тими самими.
- Новий час проходить ті самі валідації, що новий запис: `Availability`, `OpeningHours`, тривалість послуги, time-block і ліміт активних крісел. Звільнення старого слота й бронювання нового виконуються атомарно; конкурентний конфлікт повертає 409 без часткового переносу.
- Команда записує `AppointmentRescheduled` з `appointmentId`, актором, старим і новим часом у тій самій транзакції. Подія доповнює журнал зміни, але не створює новий `AppointmentBooked`, скасування або другий візит у CRM; `CancellationRate` не враховує перенесення.
- Повторний submit з тим самим запитом або застарілим часом не виконує подвійний перенос; клієнт отримує актуальний стан після конфлікту.

## Why

Перенесення не повинно реалізуватися як «скасувати старий запис + Create новий». Такий підхід змінює ID, псує історію, може зкинути погоджену ціну або оплату, дублює запис у CRM/аналітиці та неправдиво підвищує скасування. Окрема доменна команда робить перенесення зміною часу того самого візиту й зберігає всі зв’язки.

## Поточний зріз (2026-09-26, клієнтський ланцюг e2e + фікс ідемпотентності споживача)

- `RescheduleAppointment` (`apps/api/src/scheduling/application/reschedule-appointment.use-case.ts`) — єдина команда: барберу 400, запис не знайдено 404, термінальний статус → `InvalidTransitionError` (409), тривалість незмінна, дата `YYYY-MM-DD` і валідна `Date` (неможливі дати на кшталт `2026-99-99`, що проходять regex, ловляться гардом NaN), новий слот — той самий `SlotValidator` (графік барбера, OpeningHours, тривалість). Депс — порти, без uow: транзакцією володіє mover.
- `PrismaAppointmentTimeMover` (`infrastructure/prisma-appointment-time-mover.ts`) — атомарний move: власна Serializable-транзакція (за ambient-транзакцією — в ній), конфлікт барбера (крім себе) + ліміт активних крісел, `version increment`, подія `scheduling.appointment.rescheduled` в outbox тією ж транзакцією; P2034 → `BookingConflictError` → HTTP 409 без часткового переносу. Пейлоад: `actorId/actorRole`, ISO `newStart/newEnd` від use case і ISO `oldStart/oldEnd`, штамповані з рядка DB (агрегат тримає лише HH:mm).
- `POST /admin/appointments/:id/reschedule` — вимагає `date` (400); мапінг `AppointmentNotFoundError`→404, `InvalidTransitionError`/`BookingConflictError`→409, `InvalidSlotError`→400. Статус-метод `AppointmentLifecycle.reschedule` (T-042) залишено, контролер на нього більше не маршрутизує.
- `POST /appointments/:id/reschedule` (T-4533 e2e-шлях, `ClientAppointmentsController`; попутно `POST /appointments/:id/reference` — REF-WEB-04) — той самий use case, але `actorRole` примусово `'client'`: роль із DTO ігнорується (клієнт не видасть себе за адміна/барбера). Власна карта помилок → HTTP; власне володіння записом — за identity-гардом `/appointments/*` (наступний крок).
- Покриття: unit `reschedule-appointment.use-case.spec.ts` (11 тестів, 100% файлу) + e2e `reschedule-appointment.e2e.spec.ts` (5: персистентність часу/статусу, outbox ISO старий/новий, перенос клієнтом, конфлікт 409 без зміни старого часу, адмін-валідація барбер 400 / без дати 400 / 404, completed→409) + ланцюг `appointment-reschedule-chain.e2e.spec.ts` (5: клієнтський POST → use case → агрегат → подія в outbox → еталонний споживач apply/duplicate; роль із DTO проігнорована; 400/404). **Знайдено і виправлено баг еталона T-042c**: duplicate-детекція працювала лише проти юніт-мока; реальний Prisma upsert повертає наявний рядок, тож повторна доставка повторно застосовувала подію — тепер `findUnique` до claim в одній транзакції релея. Паралельні прогони — client-retry контракт (P2034 → 409/500 → повтор) у `book()` і ланцюзі; `maxWorkers: '40%'` після +6 тестів (485/485, 102 сюїти).
- Залишилось: identity-гард `/appointments/*` (клієнтська сесія + власне володіння записом — сейчас actorId з DTO), UI web/mobile/адмін-календар + T-4524a drag&drop через цей use case, депозитна поведінка (разом із платіжним контуром); еталонний споживач доведений ідемпотентним на `rescheduled` e2e — нові споживачі (T-061: аналітика, CRM) копіюють патерн.

## Risks

- [ ] **Cancel-and-recreate**: заборонений шлях міг би змінити ціну, оплату або CRM-історію; unit-Tests фіксують стабільність `appointmentId` і всіх зв’язків
- [ ] **Проміжний слот**: некомітний порядок update/delete/create може відпустити старий час без нового; use case виконує move атомарно
- [ ] **Подвійний клік і застарілий календар**: 409 з оновленими слотами та idempotency/expected-version захищають від повторного переносу
- [ ] **Побічні ефекти**: підписники повинні обробляти `AppointmentRescheduled` ідемпотентно; `AppointmentBooked`/`Cancelled` з reschedule не генеруються
