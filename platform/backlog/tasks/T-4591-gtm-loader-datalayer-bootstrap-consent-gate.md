# T-4591 · GTM-завантажувач, bootstrap `dataLayer` і consent-гейт

- **Stage**: M2 (перед фазою 3 — сайт) · **Tags**: frontend, analytics, privacy, integration · **Complexity**: middle · **Depends on**: T-4590, T-4402
- **StoryPoints**: 5

## What

Точка входу аналітики в `apps/web`: ініціалізація `window.dataLayer`, **єдине** місце завантаження `gtm.js` і жорсткий consent-гейт — до згоди користувача GTM у мережі не йде взагалі.

### Bootstrap (одна точка монтування)
- `src/app/layout.tsx` (RootLayout) монтує один клієнтський компонент `<AnalyticsBootstrap />` (поруч з `AuthProvider`) — замість «init у layout», як пропонує T-4575 для Amplitude. Один провайдер = один push-контракт (T-4595), без розмазування ініціалізації по компонентах.
- Ініціалізація: `window.dataLayer = window.dataLayer || []` + базовий `consent: 'default'` (див. T-4600) — виконується **до** будь-якого `gtm.js`.

### Завантаження GTM
- Скрипт через `next/script` (`strategy="afterInteractive"`) з `NEXT_PUBLIC_GTM_ID`, з `data-cfasync="false"`.
- Оточення: якщо `NEXT_PUBLIC_GTM_ID` порожній або `NODE_ENV !== 'production'` — скрипт **не** завантажується взагалі. Локальна розробка не пише в GA4 за замовчуванням.
- `<noscript>`-фрейм GTM навмисно **не** додається: у GA4 none noscript-пікселя, а сам фрейм не дає вимірювання — тільки перевірку cookie-ів GTM. Підстава рішення зафіксована тут, щоб не «додавали за інструкцією з інтернету».
- Клієнтські ідентифікатори (`session_id`, `anon_id`) ініціалізуються тут же, синхронно, у пам'яті + `sessionStorage` — щоб `page_view` міг їх прочитати.

### Consent-гейт
- `useConsent()` з T-4402 — єдине джерело рішення. Стани: `'unknown' | 'granted' | 'denied'`.
- Поки стан не `granted` — `gtm.js` не завантажується (жодного звернення до `googletagmanager.com`). Жодних «cookieless pings» до згоди: T-4402 вимагає «трекери не завантажуються до згоди», тому GA4 не отримує жодних даних (найсуворіша приватність, втрата consent-mode моделювання — свідомий компроміс).
- Повторна згода/відмова не перезавантажує скрипт: після завантаження рішення йдуть через `consent_update` (T-4600), GTM-tags реагують на зміну, а не на перезавантаження.
- Поки T-4402 не реалізований — гейт працює як no-op із типом `ConsentState`; це дозволяє мержити обидва PR без dependencies від порядку.

## Why

Три технічні пастки, кожна з яких ламає аналітику непомітно: (1) GTM без consent-гейта порушує DSAR-політику з T-4402; (2) скрипт, вантажений двічі (bootstrap + компонент), дає подвійні `page_view`; (3) dataLayer, ініціалізований після першого пушу, губить перші події. Один bootstrap з гейтом закриває всі три.

## Done

- [ ] `window.dataLayer` ініціалізується до першого пушу; перший пуш не губиться
- [ ] `gtm.js` вантажиться рівно один раз, лише після `consent = granted`, лише в production
- [ ] Локально (`NODE_ENV=development`) і при порожньому `NEXT_PUBLIC_GTM_ID` — жодного звернення до `googletagmanager.com` (перевірка Network tab)
- [ ] Банер «Відхилити» → GTM не вантажиться; «Прийняти» → вантажиться; зміна рішення не перезавантажує скрипт
- [ ] `<noscript>`-фрейм GTM відсутній (рішення зафіксоване)
- [ ] `session_id`/`anon_id` — UUID у форматі, стабільні в межах сесії, `session_id` змінюється на новій сесії
- [ ] Коріння `layout.tsx` містить рівно один `<AnalyticsBootstrap />`; жоден інший компонент не ініціалізує dataLayer
- [ ] Юніт-тест: без згоди dataLayer отримує тільки bootstrap-подію, `gtm.js` не завантажується

## Risks

- [ ] **Публікація без GTM**: якщо контейнер порожній, сайт працює без збору — не блокер, але зафіксувати в T-4603, що аналітика «тиха»
- [ ] **Пізній `gtm.js`**: consent-банер на 100vh першого екрана дає ~1–2 с нульових даних на перший `page_view`; виправлення — `consent_update` до завантаження, а не ілюзія повноти
- [ ] **complexity `/account`**: кабінет у тому ж застосунку, тому GTM з'явиться і там; це прийнятно (GA4 = маркетинговий контур), але події кабінету відсікаються явно (T-4596)
