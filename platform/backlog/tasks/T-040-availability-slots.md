# T-040 · Availability, слоти, інваріант 2 крісел

- **Stage**: M1 (phase 4) · **Tags**: backend, high-risk · **Complexity**: senior · **Depends on**: T-022, T-023

## What

Ядро `scheduling`: TimeSlot (крок 15 хв), валідація «вільний» = `Availability` барбера + `OpeningHours` локації + інваріант 2 крісел − тривалість послуги. «Будь-який барбер» = агрегат по барберах локації.

## Why

Серце запису; той самий валідатор перевикористовується walk-in, waitlist, живими слотами.

## Розбивка (слайси, критичний шлях M1)

1. **Слоти одного барбера** *(middle)* — Availability + OpeningHours − тривалість послуги; флоу запису вже можна тестувати на одній кріслі. Чиста валідатор-логіка без конкурентності.
2. **«Будь-який барбер»** *(middle)* — агрегат по барберах локації + підстановка конкретного при бронюванні.
3. **Інваріант 2 крісел + конкурентність** *(senior)* — конфлікти між барберами, транзакційні блокування, race-condition-Tests на подвійне бронювання. **Єдине senior-ядро задачі**: без нього система бреше клієнту, з ним — найтонші місця (ізоляція транзакцій, ідемпотентність повторних запитів).

## Поточний зріз

API слоти приймають фактичну дату (`YYYY-MM-DD`), фільтрують зайнятих барберів і крісла, а бронювання зберігає дату/час як UTC timestamp. Вставка перевіряє barber overlap і активну місткість крісел у serializable транзакції; конфлікт повертає 409. Юніт та PostgreSQL e2e покривають межі й паралельні запити. Залишилося перевикористати ядро у walk-in/waitlist і повторити performance замір на цільовому середовищі.

- **2026-11-10 — верифікація і закриття**: `jest src/scheduling src/booking --testPathIgnorePatterns=/e2e/` — 48 сюїт / 202 Tests зелені (межі вікон, крок 15 хв, вихідні дні, перехід між днями, місткість крісел). E2E на Postgres: `admin-bookings.e2e.spec.ts` підтвердив, що з двох одночасних запитів за останнє крісло проходить один (201 + 409), `booking-flow-gwt.e2e.spec.ts` — що зайняті барбери відсіюються і «Будь-який» віддає реальних вільних. `scripts/benchmark-scheduling.ts` не компілювався (застарілий виклик `BarberSchedule.create(id, loc, windows)`) — виклик приведено до поточної сигнатури; 5 барберів валідуються за 0.13 мс. Замір на Docker dev API повторити не вдалося: контейнер `fade-platform-api` падає через недомігровану dev-DB — це стан середовища, не коду; історичний замір 10.2–84.8 мс лишається чинним до повтору на цільовому середовищі.

Слайси 1 і 2 — паралельно з першого дня (можна віддати middle-розробнику під наглядом); 3 — після 1, бо залежить від моделі крісел, і робить той, хто писав 1. Senior-рішення тут — не «написати валідатор», а вибрати механізм конкурентності (SELECT FOR UPDATE vs optimistic locking з retry) і захистити його тестами.
