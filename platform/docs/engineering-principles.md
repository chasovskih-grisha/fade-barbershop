# Інженерні принципи розробки

> Як ми пишемо софт цієї платформи: принципи, жорсткі обмеження і політики тестування. Документ — частина Definition of Done: рев'ю перевіряє код проти цього файла так само, як проти acceptance criteria. Джерела архітектури — `architecture.md` і `docs/adr/`; цей документ — про **як тримати код добрим**, поки фази 0–27 його пишуть.

## Чому це окремий документ

Каркас фіксує межі (контексти, шари, події), але не якість всередині меж. Без явних правил моноліт з 16 контекстами перетворюється на legacy швидше, ніж мікросервісний зоопарк: «ще один if» у домені, «ще один рядок у файлі на 400 рядків», «тест додам пізніше». Тут ці три спокуси заборонені явно.

## Принципи і як вони читаються тут

| Принцип | Що означає саме тут | Де перевіряється |
|---------|---------------------|------------------|
| **DDD ( tactical )** | Мова коду = `ubiquitous-language.md`. Агрегат — один на транзакцію; інваріанти — в домені, не в сервісах; команди — мовою домену (`book`, `confirm`, `reschedule`), не `setStatus`. Домен не імпортує Nest/Prisma/HTTP (шарність `architecture.md`). | Рев'ю README контексту vs код |
| **SOLID** | S: use case = один клас/функція = одна причина зміни. O: нова поведінка = новий обробник події або реалізація порту, не правка switch. L: реалізації портів (`AcquiringGateway`, `PhotoRepository`, `OtpSender`) взаємозамінні, включно з фейками для тестів. I: порти вузькі — окремий порт на інтеграцію, не «ExternalServices». D: `application/` залежить від інтерфейсів, `infrastructure/` — від реалізацій; збирання — в composition root (`main.ts`). | Рев'ю портів і обробників |
| **DRY** | Бізнес-правило живе в одному місці. Формула ціни — в домені `scheduling`/`billing`, не в контролері, mobile-клієнті і дашборді одночасно; read-моделі повторюють *дані*, не *логіку*. Дубль у тесті — терпимий (тест читається окремо), дубль у проді — ні. | Grep-рев'ю: правило існує в одному файлі |
| **UUID Keys** | Усі доменні моделі (агрегати, ентіті, read models, події) використовують **UUID v7** як primary key. Заборонено auto-increment Int PK на доменних таблицях. Генерація — client-side (shared kernel `uuidv7()`). Міграція існуючих — expand/contract (ADR 0021). | Рев'ю Prisma схем / лінтер: `@@id` на `uuid` |
| **KISS** | Найпростіше рішення, яке проходить AC. Немає CQRS-фреймворків, Event Sourcing, GraphQL, мікросервісів — вони свідомо відхилені (`architecture.md`, ADR 0002). Патерн з'являється тоді, коли без нього болить, а не «про запас» (AGENTS.md). | Рев'ю на over-engineering |
| **YAGNI** | Нічого «на майбутнє»: друга локація — фаза 9, і її абстракції з'являться у фазі 9. Параметри конфігу вводяться, коли є друге значення. Табу: узагальнені репозиторії, «універсальні» фабрики, плагінні системи без другого плагіна. | Рев'ю: «де другий кейс?» |
| **Failure handling** | Події — at-least-once: кожен обробник ідемпотентний (ключ події; патерн ADR 0009/0012/0016). Зовнішні виклики — через ACL з таймаутом і ретраями; невизначений результат зовнішнього виклику — стан, а не виключення. | Рев'ю обробників подій |

## Генерація ID (ADR 0021)

Усі доменні моделі генерують ідентифікатори на клиентській стороні через `uuidv7()` з пакета `@fade/domain-shared`:

```typescript
import { uuidv7, DomainId } from '@fade/domain-shared';

type AppointmentId = DomainId<'AppointmentId'>;
const id = uuidv7() as AppointmentId;
```
Заборонено використання `autoincrement()`, DB-дефолту (`@default(uuid())`) або
`crypto.randomUUID()` (v4) для доменних сутностей.

### §UUID Keys: що перевіряється автоматично (T-4300f)

Політика тримається двома гейтами — редактор і CI перевіряють те саме:

1. **ESLint `eslint-plugin-uuid-keys`** (`error` у `apps/api/.eslintrc.js`):
   - `no-random-uuid` — забороняє `randomUUID()` / `crypto.randomUUID()` /
     `v4()` / `uuid.v4()`; дозволений лише `uuidv7()` зі shared kernel;
   - `no-readable-id` — забороняє читабельні id (`id: 'loc-1'`,
     `locationId: 'loc_KYY_01'`) у полях `id` / `*Id`; винятки — опція
     `allow` (Swagger-приклад, плейсхолдери fake-провайдерів).
   Тестові двійники, фікстери, `.env.ts`, `*-setup.ts` і сіди поза гейтом:
   читабельний ключ там — вхід `seedUuid()`, а не id у БД.
2. **CI `pnpm uuid:check`** (`scripts/check-uuid-keys.mjs`, крок у `style`):
   - Prisma: `Int`/`BigInt` PK, `autoincrement()`, DB-дефолт id, PK без
     `@db.Uuid`, складений `@@id` — падає; дозволено `String @id @db.Uuid`;
   - код: `randomUUID()`/`v4()` у `domain/`/`application/` і IdGenerator-
     адаптерах, читабельні id в API-коді.
   Інфраструктурні винятки — явні allowlist-и з причиною в скрипті:
   `AppSetting` (натуральний ключ), трасування запитів, ключі об'єктів
   сховища, handle зовнішніх job, статичний демо-каталог.

Обидва гейти — «червоний білд», не домовленість; новий виняток додається
рядком у allowlist з причиною, а не вимкненням перевірки.

## Жорсткі обмеження (перевіряються автоматично)

1. **Target LOC < 100 на файл.** Кожен файл — одна відповідальність, яку видно без прокрутки; великий файл = сигнал, що всередині ховається другий клас, другий use case або змішані шари. Деталі, винятки і механіка розбиття — **ADR 0019**.
2. **Цикломатична складність функції ≤ 10.** Понад — розбити на функції з іменами мовою домену; це тримає функції тестовими і читабельними.
3. **Параметри функції ≤ 3**, далі — об'єкт-параметр з іменем з ubiquitous language.
4. **Публічний API пакета** (те, що імпортують сусіди): чим менший, тим краще; реекспорт — явний, `index.ts` не стає сміттєзвалищем.

Обмеження 1–3 — правила лінтера з першого дня (T-001): порушення = червоний білд, не «домовленість». Правило ≠ мета: якщо чесне рішення не влазить у 100 рядків, спочатку шукаємо другий клас усередині; роздуті абстракції заради лічильника рядків заборонені так само, як і довгі файли.

Форматування коду — не предмет рев'ю: **Prettier** (`pnpm format:check`) — гейт CI. Редакційна проза (`docs/`, `backlog/`) — поза Prettier (`.prettierignore`); код і конфіги — обов'язково.

## Запахи коду і політика рефакторингу

Гейти вище ловлять наслідок (файл, складність, арність). Цей каталог — типові *причини*, зведені під час рефакторингу CRM/content/identity/scheduling (2026-09): кожен пункт — те, що реально зустрілося в кодовій базі, з канонічним способом лікування. Запах ≠ дефект: це сигнал шукати причину, а не розмазувати симптом.

| Запах | Як виглядає | Що робити |
|-------|-------------|-----------|
| **God-файл** | Один файл тримає VO-типи, мапінг рядків Prisma і фабрику одночасно; гейт LOC спрацьовує, а «розмазати» по шарах нічого не дає | Шукати всередині другий клас/шар і виносити за відповідальністю: типи значень → `*.types.ts`, мапінг рядків → `*-row.ts`, публічний API — явний `index.ts`, а не сміттєзвалище реекспортів |
| **Позиційні залежності** | Конструктор або приватний метод на 4–5 аргументів: `new Handler(articles, outbox, clock, uow)` — при читанні виклику не видно, що є що | Bundle-об'єкт deps з іменованими полями (`PublishArticleDeps`, `CrmCommandContext`); збирати його один раз у composition root (module), контролеру ін'єктувати через Symbol-токен |
| **Дубль бізнес-правила** | Та сама формула/перевірка в контролері, use case і сусідньому контексті (`(day + 6) % 7` — 8 примірників) | Один доменний хелпер поруч із моделлю, якої стосується правило (`scheduling/domain/day-of-week.ts`) + спека, що фіксує семантику; грепнути по формулі перед мерджем |
| **Крихкий payload події** | Тип payload — `interface`: компілятор мовчки пропускає зайві й перейменовані поля у літералі | Тип payload події — `Record<string, unknown>`, літерал — явний у конструкторі події з bundle-props; контракт між контекстами — snapshot-тест |
| **Змішана валідація** | Одна функція на складність 14, де кожен `if` — окреме правило вводу | Розбити на функції-перевірки з іменами мовою домену (`assertTitle`, `assertBody`, `assertExcerpt`); оркестратор лишається лінійним |
| **Нечілький недосвіт** | Невикористані імпорти/змінні, залишки перейменувань — гаснуть лише в eslint | Прибирати в тому ж PR, що й причину; `as any` у шарі infrastructure — з коментарем «чому безпечне» |
| **Тест не конструюється** | Спека будує хендлер позиційно, і будь-яка зміна deps ламає всі специфікації одразу | Специфікації конструюють хендлер так само, як prod: той самий bundle-deps; setup-хелпер (`content-spec-setup.ts`) — один на контекст |

Порядок рефакторингу незалежно від запаху: спершу зелений тест на поточну поведінку → потім переструктурування → потім ті самі тести зелені без правок assert-ів. Рефакторинг без тесту — це переписування, а не рефакторинг.

## Політики тестування

### Піраміда

```
        ╱  e2e (Playwright)   ╲   ≤ 10%  — GWT-сценарії booking-flow-tests.md
       ╱── functional (API) ──╲─  ~25%  — use cases через HTTP з реальними адаптерами (крім зовнішніх ACL)
      ╱──── unit (домен) ──────╲  ~65%  — домен, VO, обробники; швидкі, без БД/HTTP
     ╱──────────────────────────╲
```

### Ковередж — гейт CI, не побажання

| Зона | Лінія | Коментар |
|------|-------|----------|
| `apps/api/src/*` | **≥ 85% рядків, ≥ 80% гілок** | Гейт PR; домен і application — ≥ 90% |
| `packages/*` | ≥ 85% | Контракти — повний (типи самі собою тест) |
| `apps/web`, `apps/admin` | ≥ 70% | Компоненти + серверні екшени |
| `apps/mobile` | ≥ 60% | UI-логіка; рендер-деталі — через e2e |

Падіння нижче лінії = червоний білд. Новий файл без тестів не проходить рев'ю навіть коли загальний відсоток високий.

### Що обов'язково тестується (кожен шар — своїми тестами)

- **Домен**: інваріанти агрегатів (слот не перевиділяється, ціна не змінюється після снепшота, лічильник лояльності скидається), доменні події як результат команд. Без моків БД — домен їх не знає.
- **Application**: use case = транзакція, outbox-запис, ідемпотентність обробника на повторній доставці (штучна повторна доставка — патерн ADR 0009), відкат при невдачі.
- **Infrastructure (ACL)**: кожен зовнішній провайдер має **фейк** (in-memory реалізація порту) для тестів і dev-середовища: `FakeOtpSender`, `FakeAcquiringGateway`, `FakeAiGenerationGateway`. Реальні провайдери — лише в e2e-sandbox і проді.
- **Functional (API)**: сценарій через HTTP: OTP → запис → оплата → завершення → події споживачам; перевірка семантики помилок (що клієнт бачить) і станів.
- **E2E**: GWT-сценарії `booking-flow-tests.md` по екранах + регрес AC-гейтів (PAY, LYL, DSC). Mobile-гілки — ті самі сценарії (розділ mobile у booking-flow.md). Це автоматизація **T-301**.
- **Контракти**: події між контекстами — snapshot-тести схем (v1 поломки версіонування ловляться до релізу).

### Правила якості тестів

1. Тест читається як специфікація: ім'я — речення мовою домену («other_client_cannot_read_foreign_visit»), AAA-структура, один assert-блок на поведінку.
2. Немає sleep-ів у тестах; час — за ін'єктованим `Clock`.
3. Shared fixture без контексту — заборонений: набори даних збираються під сценарій.
4. Тест падає → спершу фікс поведінки або теста, ніж нова фіча; flaky-тест виправляється або видаляється у тому ж спринті — quarantine довше одного тижня заборонений.

## Міграції без downtime (гейт T-4812)

Схема і код деплояться разом, але інстанси API оновлюються по одному (rolling
deploy): поки живе старий інстанс, схема вже нова. Тому кожна міграція мусить
бути **сумісною з попереднім кодом**; зміна, що цього не робить, іде двома
кроками **expand → contract**:

1. **Expand** (разом із випуском): додати nullable-колонку / нову таблицю /
   індекс; код пише і в старе, і в нове поле.
2. **Contract** (наступним випуском, коли старий код більше не читає поле):
   прибрати поле / `SET NOT NULL` / перейменувати.

Гейт `pnpm db:migration:check` сканує `apps/api/prisma/migrations/*/migration.sql`
і червонить на операціях, які одним кроком ламають старий інстанс:
`DROP TABLE`, `DROP COLUMN`, `TRUNCATE`, `DELETE FROM`, `RENAME`,
`SET NOT NULL`, а також `ADD COLUMN ... NOT NULL` без `DEFAULT`. Дозволене —
`ADD COLUMN` (nullable або з `DEFAULT`), `CREATE TABLE`, `CREATE INDEX`,
`ALTER COLUMN ... TYPE`. Виняток — рядком у `ALLOWLIST` скрипта з причиною,
а не вимкненням перевірки.

## Що це дає (зв'язка з беклогом)

- LOC/складність/ковередж — у лінтері з **T-001**; піраміда і фейки — з першого use case (**T-010**); e2e-автоматизація — **T-301**.

- Дашборд якості (ковередж, розміри файлів) — частина **T-300** (моніторинг і безпека).
- Щоденний інструмент — PR-чекліст рев'ю (`review-checklist.md`): принципи цього документа у формі «так/ні» для рев'ювера.

## Антипатерни, які ламають цей документ

- «Тимчасовий» файл > 100 рядків, який ніхто не розбиває.
- Інваріант, перевірений у контролері, бо «так швидше».
- Мок усе-в-одному замість фейка порту.
- Тест, що перевіряє реалізацію (приватні методи), а не поведінку.
- Погоня за ковереджем: автогенеровані тести геттерів заради відсотка.
