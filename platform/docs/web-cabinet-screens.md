# Екрани кабінету клієнта (web) — вхід, профіль, візити

> Специфікація екранів кабінету `apps/web` (SSR) — у тому самому стилі, що `admin-screens.md` і `booking-flow.md` (**Layout, Компоненти, Стани, Критерії**). Маршрути з `products.md` §1: **`/login`** (телефон → SMS-код, ADR 0005), **`/account`** (профіль), **`/account/appointments`** (візити з діями). Публічні сторінки — `web-screens.md`; mobile-дзеркало — `client-screens.md`; флоу запису — `booking-flow.md` (окремий документ: `/booking` тут не специфікується).
>
> Мова — українська. Той самий `User`, що в додатку (ADR 0005): вхід на сайті = вхід в акаунт мережі. Барбер і admin у кабінет гостя не логіняться. Аналітика (GA4/Meta) — events «успішний OTP», «CTA запису» (products.md §1).

## 1. `/login` — вхід за телефоном (ADR 0005)

- **Layout**: центрований макет ~400 px (та сама колонка, що майбутній `/gift`-чекараут): крок 1 — форма телефону; крок 2 — форма коду. Переходи між кроками без перезавантаження (SSR-фрейм або клиентська гілка).
- **Компоненти**:
  - Крок 1: інпут телефону (маска `+380 XX XXX XX XX`), кнопка **«Отримати код»**, примітка «Ми надішлемо SMS з кодом»;
  - Крок 2: інпут коду (5–6 цифр), кнопка **«Увійти»**, рядок **«Надіслати ще раз»** зі зворотним відліком (60 с, ADR 0005 «ліміти повторної відправки»), посилання «Змінити номер» (назад до кроку 1);
  - Дислеймер персональних даних (телефон = логін, `business/legal-ua/personal-data.md`).
- **Стани**:
  - новий номер — реєстрація = перший успішний OTP: створюється `User` з роллю `client` (ADR 0005, п. 3); UI той самий, без окремої реєстрації;
  - невірний код → помилка біля поля; вичерпані спроби → блокування перебору з таймером (ADR 0005 «спроби, блокування перебору»);
  - повторна відправка → disabled до кінця відліку; TTL коду 5 хв (ADR 0005);
  - dev-середовище — код у логах (`OtpSender` = console, ADR 0005);
  - loading — спінер на кнопці; SMS не дійшов → «Надіслати ще раз» після відліку.
- **Успіх**: `Session` = httpOnly cookie (окремий cookie-name від admin, ADR 0005) → redirect на `/account/appointments` (або на `?next=` URL, з якого прийшов вхід).
  - **Правило guard-а (T-4718)**: неавторизований запит до шляху кабінету → redirect на `/login?next=` цей шлях. Шляхи кабінету: `/account`, `/account/appointments`, `/account/devices`, `/account/referrals`. Значення `next` проходить `safeNextPath`; усе, що хелпер відкидає (зовнішній або protocol-relative шлях), → дефолт `/account/appointments`. `/login` ніколи не є `next`.
- **Критерії**: ADR 0005 (нормалізація E.164 `+380`, TTL, ліміти, сесії по поверхнях, «пароля в клієнта немає»); рольова межа products.md §1.

## 2. `/account` — профіль

- **Layout**: заголовок «Мій профіль» → картка **«Найближчий візит»** → секції: **Акаунт** → **Вподобання** → **Сповіщення** → **Мої відгуки** → **AI-підбір зачіски** → **Лояльність** → **Реферали** → **Сертифікати**. Секція без даних — ховається (крім «Акаунта»).
- **Бічне меню — єдина навігація** (T-4732): перехід між розділами кабінету (`/account`, `/account/appointments`, `/account/devices`, `/account/referrals`) — лише через aside кабінету (`AccountShell`), і його чотири ярлики лишаються незмінними: Профіль, Мої візити, Пристрої, Реферали. Тіло профілю не малює другої копії цього меню: жодних списків «Мої візити» / «Пристрої» / «Реферали» в секціях. Наявне посилання **«Реферальна програма»** на `/account/referrals` (секція «Реферали») — це один текстовий перехід, а не меню. Дзеркало в застосунку — `client-screens.md` §5.
- **Правило незбережених змін** (T-4733): якщо ім'я або нотатка вподобань у полі відрізняються від **останнього збереженого** значення і клієнт відкриває інший екран кабінету, профіль питає **«Зберегти зміни?»** з трьома відповідями: **«Зберегти»** (надсилає наявний запит збереження і після успіху переходить), **«Не зберігати»** (переходить, введене відкидається) і **«Залишитись»** (лишає на профілі, введене не втрачається). Невдале збереження лишає клієнта на профілі з його текстом і показує помилку секції — перехід не відбувається. Питання не виникає для перемикачів сповіщень (вони зберігаються одразу, T-4722), для виходу (T-4723) і для форми без змін. Це питання в продукті, а не браузерний `beforeunload`. Дзеркало в застосунку — `client-screens.md` §5.
- **Компоненти**:
  - **Найближчий візит** (T-4716): найближчий майбутній візит із того самого списку, що вантажить `/account/appointments`. Рядок 1 — день тижня і дата, час початку–кінця, у `uk-UA`; рядок 2 — послуга, барбер, локація. Посилання **«Деталі»** веде на `/account/appointments` (не відкриває перенос). Візит у стані «Очікує депозиту» зберігає бейдж-попередження, як на сторінці візитів; кнопки оплати тут немає. Майбутнього візиту немає — один рядок **«Немає найближчого візиту»** і посилання **«Записатися»** на `/booking`.
  - **Акаунт**: ім'я (редаговане, збереження одразу або кнопкою; **одне** ім'я з застосунком — джерело профіль `identity`, не друга копія на екрані), телефон (read-only — логін за ADR 0005; кнопка **«Змінити номер»** відкриває наявний флоу — див. «Правило номера» нижче; підтримку для цього не залучаємо), кнопка «Вийти».
    - **Правило імені**: збереження тримить значення; порожнє після триму — «Вкажіть ім'я» і збережене ім'я не замінюється (пробіли — не очищення); після успішного збереження відкритий екран показує збережене ім'я, **включно із заголовком кабінету**, без ручного перезавантаження; англійський рядок валідації з web-роута клієнт не бачить. Дзеркало в застосунку — `client-screens.md` §5.
    - **Правило запиту імені** (T-4726): запит показується **лише коли збережене ім'я порожнє** — тоді профіль питає **«Як до вас звертатись?»** і пропонує поле імені. Підпис у заголовку кабінету **«Клієнт»** — це запасний текст для показу: він ніколи не зберігається і не стає іменем клієнта. Запит — не модальне вікно і не гейт: решта секцій профілю лишається робочою, і клієнт може піти зі сторінки, не ввівши ім'я. Дзеркало в застосунку — `client-screens.md` §5.
    - **Правило лічильника візитів** (T-4734): під іменем стоїть один рядок **«Візитів: N»**, де N — кількість **минулих** візитів із того самого списку, що вантажить `/account/appointments`; окремого запиту екран не робить. Нуль показується як **«Візитів: 0»** і не ховається. Запит візитів упав — рядка немає (нуль на місці помилки не показуємо). Це не список візитів і не картка найближчого візиту (T-4716). Дзеркало в застосунку — `client-screens.md` §5.
    - **Правило номера** (T-4720): поточний номер на екрані read-only. Кнопка «Змінити номер» викликає **той самий** наявний use case, що вже замінює номер (`POST /identity/phone/change/request` і `POST /identity/phone/change/verify`, T-4620a/b), — це не «ще один логін» і не друга копія користувача. Крок 1 — новий номер; крок 2 — код з SMS **нового** номера; невірний код лишається на кроці коду; номер, що вже належить іншому клієнту, відхиляється без імені цього клієнта. Успіх гасить локальну сесію і веде на `/login`, а наступний вхід — уже з нового номера. Екран не ревокує сесії повторно: інші сесії скасовує сама команда. Дзеркало в застосунку — `client-screens.md` §5.
    - **Правило виходу** (T-4723): вихід — **один** контрол із підписом «Вийти», у бічному меню кабінету; у заголовку профілю другої кнопки виходу немає. Перед виходом екран питає **«Вийти з цього пристрою?»** з кнопками **«Вийти»** і **«Скасувати»**; «Скасувати» лишає сесію як була і не закриває профіль. Підтвердження завершує **лише локальну** сесію і веде на `/login`; воно не викликає revoke-all, тож інші пристрої лишаються в акаунті (їхній список — T-4724). Перемикачі сповіщень вихід не змінює: вимкнення push — це перемикач із «Сповіщення» (T-4722), не вихід. Дзеркало в застосунку — `client-screens.md` §5.
    - **Правило пристрою** (T-4724): у секції «Акаунт» стоїть один рядок **«Цей пристрій»** — канал поточної сесії та посилання на екран пристроїв `/account/devices` (той самий, що в бічному меню). Коли список пристроїв завантажено і в ньому є інші пристрої, рядок показує **«Ще {N}»**, де N — кількість інших пристроїв; при N = 0 або поки список не завантажено лічильника немає. Запит списку впав — посилання «Цей пристрій» лишається, лічильник відсутній. На рядку немає дії відкликання сесії: відклик живе на екрані пристроїв, не в профілі. Дзеркало в застосунку — `client-screens.md` §5.
  - **Вподобання** (T-4721): textarea «Алергії, уподобання, побажання» (вільний текст; показує барберу в картці клієнта — `barber-screens.md` §4.3). Одна нотатка, що зберігається як **не більше 20 непорожніх рядків**, кожен **до 100 символів** після триму (порожні рядки відкидаються). Підказка **«Цей текст побачить ваш майстер перед візитом»** — частина секції на обох поверхнях. Понад ліміт екран показує **«Не більше 20 рядків, до 100 символів у рядку»** і запиту не надсилає. Порожня нотатка дозволена і очищає збережені рядки. Дзеркало в застосунку — `client-screens.md` §5.
    - **Правило цитати нотатки** (T-4731): під полем стоїть read-only цитата **останньої збереженої** нотатки — збережені рядки, з'єднані так, як їх написав клієнт. Це не другий редактор і не дзеркало textarea: незбережений текст у полі цитату не змінює, вона оновлюється лише після успішного збереження. Порожня збережена нотатка — один рядок **«Майстер ще нічого не побачить»**. Цитата не редагується. Дзеркало в застосунку — `client-screens.md` §5.
  - **День народження** (T-4730): необов'язкові **день і місяць**, рік не питаємо. Порожнє значення — дефолт: показуємо сам контрол без вибору, а не вигадану дату. Збережене показуємо як «12 листопада», без року. Кнопка **«Очистити»** прибирає збережене значення. Збереження не надсилає ні повідомлення, ні знижки, ні push — розсилкою дня народження володіє T-4459. Дата не показується на публічних сторінках і іншим клієнтам. Дзеркало в застосунку — `client-screens.md` §5.
  - **Сповіщення** (T-4722): чотири перемикачі — **SMS-нагадування**, **Email про візит**, **Push** і **Маркетингові пропозиції**. Значення зберігаються в профілі клієнта, обидві поверхні читають їх назад. Дефолт, доки нічого не збережено: SMS і email увімкнені, push і маркетинг вимкнені. Підпис під push на сайті говорить про **браузер**, у застосунку — про **телефон**; це той самий булевий перемикач. Вимкнений маркетинг не чіпає трьох інших каналів, а вимкнений push не виходить із акаунта. Застосунок не показує push-токен. П'ятого перемикача немає. Дзеркало в застосунку — `client-screens.md` §5.
  - **Мої відгуки** (FDB-WEB-04): список своїх відгуків (візит, зірки, текст, фото-мініатюри); видалення — до кінця вікна 30 днів (FDB-002/003); видалення прибирає фото і, якщо публікувалось, знімає відгук з сайту.
  - **AI-підбір зачіски** (AI-WEB-01…08): завантаження фото (AI-WEB-02, згода перед першою генерацією — AI-WEB-03), історія генерацій зі статусами (`pending | processing | ready | failed`), вибір варіанту → прикріпити до візиту (REF-WEB-02), видалення фото/результатів будь-коли (AI-WEB-07), офлайн/помилки — банер (AI-WEB-08).
  - **Лояльність** (LYL-WEB-01): прогрес «X/7 до безкоштовного візиту» + коротке пояснення правила (укр.); секція — лише коли фаза 11 (частина A) ввімкнена.
  - **Реферали** (RFR-WEB-01…03): «Запросити друга» — персональний код/посилання + шарінг; «Мої запрошення» зі статусами.
  - **Сертифікати** (GFT-WEB-03): «Мої сертифікати» — коди, залишки, строк дії.
  - **Секції без даних прибрані (T-4729)**: «Мої відгуки», «Лояльність» і «Сертифікати» відсутні на сторінці, доки їхні власні задачі не здадуть реальні дані (відгуки — T-151, лояльність — T-142, сертифікати — gift-задача). Порожніх карток-заглушок немає. **Реферали** на профілі — не порожня картка, а посилання **«Реферальна програма»** на `/account/referrals`, де сторінка вже існує.
- **Стани**: порожні секції — підказки («Ще немає відгуків», «Завантажте фото для підбору зачіски»); збереження — інлайн-підтвердження, без перезавантаження; loading — скелетони. Картка найближчого візиту не блокує профіль: поки список візитів вантажиться — картка тихо чекає (один спокійний рядок, не спінер сторінки); запит візитів упав — картки немає, профіль лишається робочим, помилку показує сторінка візитів (T-4716).
- **Критерії**: FDB-WEB-04 (профіль), AI-WEB-01…08, LYL-WEB-01, RFR-WEB-01…03 (фаза 21), GFT-WEB-03 (фаза 20); дзеркало mobile-профілю — `client-screens.md` §5.

## 3. `/account/appointments` — мої візити

- **Layout**: сегменти **«Майбутні | Минулі»** → список карток візитів; тап/клік по картці → розгорнута картка візиту з діями.
- **Компоненти картки в списку**: дата/час, послуга, барбер, локація, статус-бейдж; додаткові бейджі: «Пакет» (party), «Безкоштовний» (LYL-WEB-03), «Очікує депозиту» (PAY-WEB-02).
- **Рядок депозиту в картці** (T-4737): коли `deposit.amount > 0` — сума депозиту і під нею дедлайн скасування зі снепшота візиту (`deposit.freeCancelUntil`) у часі Києва («Безкоштовне скасування до 2 жовтня о 12:00»); після дедлайну — «Вікно безкоштовного скасування минуло — депозит утримається». Дедлайн відсутній — лише сума; сума 0 або `deposit: null` — рядка немає. Діалог скасування повторює той самий наслідок (нижче).
- **Розгорнута картка візиту** — той самий підсумок, що крок 5 флоу (`booking-flow.md`): послуга, барбер, час, локація; **референс** — мініатюра, клік — повний розмір; **коментар** (REF-WEB-03/05); для party — режим, обидві ноги, ім'я сина (`PARTY-WEB-05`); розбивка ціни: базова → знижки (тип/код) → `FinalPrice` (DSC-006).
- **Дії (за станом візиту)**:
  - **Оплатити депозит** (стан «Очікує депозиту») — 30% `FinalPrice`, PAY-WEB-01/02; успіх → «Підтверджено (депозит сплачено)» + посилання на чек (PAY-WEB-04).
  - **Оплатити решту** (після послуги) — PAY-WEB-01; посилання на чеки депозиту і решти (PAY-WEB-04).
  - **Редагувати референс і коментар** — поки візит не підтверджений барбером (REF-WEB-04); після — лише перегляд.
  - **Перенести** — модальне вікно: той самий флоу вибору слота, що крок 3 `booking-flow.md`; валідація за тими самими правилами (Availability + OpeningHours + 2 крісла); **депозит переноситься на новий слот без повернення** (PAY-WEB-07); confirm-банер «Депозит переноситься». Снепшот умов (`deposit.amount`, відсоток, округлення, вікно) лишається тим самим, а `freeCancelUntil` перераховується від нового початку — дедлайн їде разом із візитом (тест `prisma-appointment-time-mover.persist.spec.ts`).
  - **Скасувати** — діалог називає лише той наслідок, який знає візит (T-4737), і сам не робить повернення коштів (refund виконує `billing` у T-091):
    - **без депозиту** — про гроші не згадує: `deposit: null` у `GET /booking/appointments` (політика вимкнена, ціна 0 або сума після округлення 0); списання й повернення коштів — T-091;
    - **депозит і збережене вікно скасування** (снепшот політики запису — PAY-ADM-09) — «Депозит повернеться», якщо скасування не пізніше вікна, «Депозит утримується», якщо пізніше; сума і дедлайн приходять зі снепшота візиту (`deposit.amount`, `deposit.freeCancelUntil`), не з константи в UI;
    - **депозит без збереженого вікна** — жодного речення про гроші, політику не вигадуємо.

    Підтвердження → статус «Скасовано»; слот автоматично пропонується черзі (`WTL-003`).
  - **Статус повернення депозита** (PAY-WEB-08): «Депозит повертається…» → «Депозит повернено» / «Повернення в обробці банку — з вами зв'яжуться»; жодних дій від клієнта не потрібно.
  - **Залишити відгук** (FDB-WEB-01…03): на завершеному візиті в межах вікна 30 днів (FDB-003) — форма: зірки 1–5 (обов'язково), текст ≤ 1000, фото до 3 шт. з прев'ю; повторне подання редагує попередній відгук (FDB-002); після подання — «Відгук надіслано»; редагування/видалення до кінця вікна.
  - **Безкоштовний візит** (LYL-WEB-02/03): позначка «Безкоштовно (7-й візит)», сума 0 грн, блок оплати не показується.
- **Стани**:
  - «Очікує депозиту» — бейдж-попередження + кнопка оплати; без успішної оплати депозиту статус лишається «Очікує депозиту», не «Підтверджено» (PAY-WEB-02);
  - expired-вікно відгуку → кнопки «Залишити відгук» немає (FDB-003); відгук надіслано → стан «Відгук надіслано» (FDB-WEB-03);
  - офлайн/помилка еквайрингу при оплаті → «гроші не списані», причина (укр.), кнопка повторної спроби (PAY-WEB-05); статус у списку оновлюється без втрати сторінки (PAY-WEB-06);
  - ідемпотентність: подвійний клік не створює другу оплату (PAY-WEB-03);
  - порожній список майбутніх — CTA «Записатися» → `/booking`; порожні минулі — «Тут з'явиться історія після першого візиту»;
  - неавторизований доступ → redirect на `/login?next=` цей шлях (правило guard-а, §1); дефолт `next` — `/account/appointments`.
- **Критерії**: PAY-WEB-01…08, REF-WEB-02…05, DSC-006/013, LYL-WEB-02…04, FDB-WEB-01…05, PARTY-WEB-05, WTL-003; статус-семантика — `scheduling` README (життєвий цикл візит + оплата).
