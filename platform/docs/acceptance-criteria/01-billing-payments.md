# 01. Оплата послуг через додаток і сайт

> Фіча: клієнт може оплатити послуги барбершопу через додаток або сайт. Контекст: `billing` (ACL еквайрингу і Checkbox), статус оплати живе на `Appointment` (`scheduling`).
>
> Події домену: `PaymentInitiated` → `PaymentCaptured` + `ReceiptIssued` / `PaymentFailed` (див. `apps/api/src/billing/README.md`).
>
> Сума оплати — **`FinalPrice`** після знижок (ADR 0007, `07-discounts.md`): `AgreedPrice` − застосовані знижки, ≥ 0. Візит з `FinalPrice = 0` — без `Payment` і **без фіскального чека**, **незалежно від причини нуля** (безкоштовний візит лояльності або 100% промокод — PAY-003; фіскальна основа — LYL-007).

> **Рішення засновника (v1): депозит при записі — 30% від `FinalPrice`**, решта (70%) — **на місці після послуги** (картка через POS/Checkbox або готівка).
> - Чому: депозит захищає від **no-show** (головний економічний злив для 2-крісельної точки), тримає фрикцію запису низькою (30% — прийнятно для преміум-сегменту); повна передоплата — найвищий бар'єр перед першим візитом, оплата після візиту — нульовий захист від no-show.
> - **Взаємодія з `AgreedPrice`** (ADR 0006): `AgreedPrice` фіксує повну ціну при записі; `FinalPrice` — після знижок (ADR 0007); **депозит = 30% × `FinalPrice`** (округлення до 10 грн, налаштовується адміном; 0 = вимкнено); решта = `FinalPrice` − депозит. Зміна ціни після запису не впливає.
> - **Взаємодія з лояльністю**: безкоштовний 7-й візит — `FinalPrice = 0` → депозит не стягується, решти немає, чек не формується (`PAY-003`, LYL-007); те саме для візиту з 100% промокодом.
> - **Політика скасувань**: своєчасне скасування (≥ 4 год до початку — **дефолт**; налаштування і скоуп — PAY-ADM-09) — депозит **повертається автоматично** на картку; no-show — депозит **утримується**; перенесення — депозит **переноситься** на новий слот без повернення. Механіка повернення (тригери, ідемпотентність, статуси, гонки, виконання через еквайринг, фіскальне реверсування) — PAY-005…010.

## Як ціна тече в оплату і чек (потік)

1. **Запис** (`scheduling`): `Appointment` = `ServiceId` + **`AgreedPrice`** (повна ціна, ADR 0006) + `AppliedDiscounts[]` (ADR 0007) → **`FinalPrice`** = `AgreedPrice` − Σ знижок, ≥ 0 — фіксується разом із записом.
2. **Депозит** (при записі): `Payment` #1 на **30% × `FinalPrice`** (округлення до 10 грн) → `PaymentCaptured` → Checkbox формує **`FiscalReceipt` #1** на суму депозиту (аванс = розрахункова операція).
3. **Решта** (на місці після послуги): `Payment` #2 на **`FinalPrice` − депозит** (картка POS або готівка) → `PaymentCaptured` → Checkbox формує **`FiscalReceipt` #2** на суму решти.
4. **Підсумок**: Σ чеків = `FinalPrice`; статус візиту «Оплачено», коли сплачені обидві частини.
5. **Візит з `FinalPrice = 0`**: жодного `Payment` і жодного чека, **незалежно від причини** нуля (LOYALTY або 100% промокод) — див. PAY-003.

## Правило (спільне)

- [ ] **PAY-001.** **`Payment` = одна платіжна транзакція** (депозит АБО решта), кожна зі своїм `FiscalReceipt`. Візит може мати 0–2 `Payment`. Сума транзакції — частина `FinalPrice`; сума всіх чеків візиту = `FinalPrice`.
- [ ] **PAY-002.** **Чек відображає фактично сплачену суму** (частину `FinalPrice` після знижок), не базову `AgreedPrice`; назва послуги — актуальна з `catalog` (сума — лише зі снепшоту).
- [ ] **PAY-003.** **`FinalPrice = 0` — без `Payment` і без чека, незалежно від причини нуля**: безкоштовний 7-й візит (маркер `FreeVisitApplied`) або знижка 100% (промокод/правило на 100%, `AppliedDiscounts` містить знижку з 100% — DSC-013). `billing` **не створює `Payment` і не викликає Checkbox** — ні на депозит, ні на решту; чеків немає (фіскальна основа — LYL-007: безоплатне надання не є розрахунковою операцією). У «Оплатах» адміна видно запис 0 грн з причиною: `loyalty` (LYL-ADM-05) або `full_discount_promo` (DSC-ADM-07) — read-запис без `Payment`. Правило виводиться з **суми** (`FinalPrice`), не з джерела: будь-який майбутній механізм з нулем на виході успадковує його автоматично.
- [ ] **PAY-004.** Статуси оплати на візиті: «Очікує депозиту» → «Депозит сплачено» → «Оплачено» (депозит + решта); проміжний стан після послуги без решти — «Очікує решти».
- [ ] **PAY-005.** **Коли спрацьовує `PaymentRefunded`**: (а) своєчасне скасування (≥ 4 год, PAY-WEB-07) — депозит повертається **автоматично**, без ручної дії; (б) адмін знімає no-show (NSH-ADM-03) — refund вручну з причиною і логом. Інших тригерів немає: перенесення переносить депозит, пізнє скасування і no-show — утримання. Refund стосується **лише захоплених** `Payment` і лише повної суми депозита (часткові повернення — поза v1). Решти (`Payment` #2) на момент скасування не існує — скасування завершеного візита неможливе (статуси не відкочуються), тому refund завжди стосується депозита.
- [ ] **PAY-006.** **Ідемпотентність refund**: один `Payment` має максимум один `PaymentRefunded`. Повторна команда (подвійний клік, retry, повторна доставка webhook) повертає той самий результат і не рухає гроші вдруге (idempotency key — як PAY-WEB-03). Сума refund ≤ захопленої суми `Payment`; refund з `failed` або незахопленого платежа неможливий.
- [ ] **PAY-007.** **Статуси повернення**: `Payment` — `initiated → captured → refunding → refunded` (terminal) або `→ refund_failed`. На скасованому візиті: «Депозит повертається…» (команда прийнята, підтвердження еквайрингу в дорозі) → «Депозит повернено» (terminal) або «Повернення в обробці банку — з вами зв'яжуться» (`refund_failed`, PAY-009). Клієнт бачить обидва стани і дисклеймер: ініціація — миттєва, зарахування на картку — до N банківських днів (залежить від банку).
- [ ] **PAY-009.** **Виконання auto-refund і збої еквайрингу**: при успішному своєчасному скасуванні команда повернення йде в `AcquiringGateway` **одразу** (без ручних дій і черг — гроші мають бути в дорозі до моменту візита). Успіх → `refunded` (PAY-007). Відмова/таймаут → **обмежені автоматичні ретраї** (за замовчуванням 3 з наростаючим інтервалом), далі — `refund_failed`: у «Оплатах» видно з причиною і кнопкою «Повторити refund» (PAY-ADM-08); клієнту push з поясненням (нейтральним) і статусом «в обробці». Типові причини (карта закрита, банк відмовив) вирішуються **поза системою** (адмін зв'язується з клієнтом, повернення готівкою/переказом — вручну) і фіксуються логом; повторний refund командою — тільки з підтвердженням адміна (захист від подвійного повернення — PAY-006).
- [ ] **PAY-010.** **Фіскальне реверсування**: refund депозита супроводжується **видатковим чеком Checkbox** на суму повернення з `related_receipt_id` на чек #1 (депозит) — інакше касова сума не сходиться. Механіка повернення ланцюга передоплати — обмеження провайдера (README `billing`, п. 3); статус видаткового чека опитується до `DONE` (як PAY-ONS-03), збої — кнопка «Повторити чек», сам refund **не відкочується**. Для no-show (утримання) реверсування немає — чек #1 лишається чинним.
- [ ] **PAY-008.** **Гонки — перший зафіксований перехід виграє**: скасування і no-show (авто або ручне) змагаються за один і той самий `Appointment`; перемагає транзакція, що завершилась першою, друга отримує конфлікт і не застосовується. Грошовий результат у гонці «пізнє скасування ↔ no-show» однаковий (утримання) — різниця лише в статусі й історії. Eligibility refund-а (≥ 4 год) оцінюється **атомарно в транзакції скасування** за серверним годинником. Скасування до підтвердження capture (запис і миттєве скасування): refund стає pending і виконується після `PaymentCaptured`; якщо capture провалиться — pending-refund анулюється (гроші не рухались).

## Web (кабінет клієнта)

- [ ] **PAY-WEB-01.** Клієнт може сплатити **решту** (70% `FinalPrice`) карткою з картки візиту в `/account/appointments` (після візиту). Перед оплатою бачить суму, назву послуги, локацію, сплачений депозит і статус.
- [ ] **PAY-WEB-02.** Під час запису після вибору слота клієнт бачить екран оплати з розбивкою: базова ціна, знижка, підсумок (`FinalPrice`) і **депозит 30%** (за замовчуванням, налаштовується). Без успішної оплати депозиту запис лишається у статусі «Очікує депозиту», а не «Підтверджено».
- [ ] **PAY-WEB-03.** Подвійний клік або повторне надсилання форми не створює другу оплату: повторна спроба з тим самим запитом повертає той самий `Payment` (ідемпотентність за idempotency key).
- [ ] **PAY-WEB-04.** При успіху депозиту: статус візиту стає «Підтверджено (депозит сплачено)», клієнту показано підтвердження і посилання на фіскальний чек на суму депозиту (Checkbox) — відкрити і скачати.
- [ ] **PAY-WEB-05.** При відмові/скасуванні на стороні еквайрингу: статус лишається «Не оплачено», гроші не списані, показано зрозумілу причину (укр.) і кнопку повторної спроби.
- [ ] **PAY-WEB-06.** Після успіху/невдачі статус у «Мої візити» оновлюється без втрати сторінки (перезавантаження допустиме, але стан має бути консистентним).
- [ ] **PAY-WEB-07.** Політика депозиту: скасування за **≥ 4 години** (дефолт вікна — PAY-ADM-09) до початку — депозит **повертається автоматично** на картку клієнта (refund через еквайринг); пізніше скасування/no-show — депозит **утримується**; перенесення — депозит переноситься на новий слот без повернення. Клієнт бачить цю політику на екрані депозиту і при скасуванні; клієнт скасовує за правилами, показаними **при записі** (снепшот політики — PAY-ADM-09).
- [ ] **PAY-WEB-08.** На скасованому візиті клієнт бачить статус повернення депозита: «Депозит повертається…» → «Депозит повернено» (PAY-007) і суму; жодних дій від клієнта не потрібно. Push про завершення повернення — PAY-MOB-05.

## Mobile — клієнт

- [ ] **PAY-MOB-01.** Ті самі сценарії, що PAY-WEB-01–06, з екрана візиту в «Мої візити» і з флоу запису.
- [ ] **PAY-MOB-02.** Якщо еквайринг підтримує — оплата через Apple Pay / Google Pay тим самим `Payment`, без окремого облікового запису платіжної системи.
- [ ] **PAY-MOB-03.** Після завершення оплати додаток повертає клієнта на картку візиту з актуальним статусом (deep link після повернення з вебв'ю еквайрингу).
- [ ] **PAY-MOB-04.** Клієнт отримує push-сповіщення про зміну статусу оплати (`billing` → подія → `notifications`).
- [ ] **PAY-MOB-05.** Push при поверненні депозита: «Депозит {сума} повернено на картку» (нейтральний текст; при утриманні push не надсилається — політика показана при скасуванні). Ті самі стани повернення на картці візиту, що PAY-WEB-08.

## Mobile — барбер

- [ ] **PAY-BARBER-01.** За рішенням про прапорець (див. «Відкриті питання»): барбер бачить у картці візиту лише стан «Оплачено / Не оплачено» без сум і деталей мережі. Без рішення — барбер нічого про оплату не бачить.

## Оплата на місці — решта 70% і walk-in (POS / готівка)

- [ ] **PAY-ONS-01.** Форми оплати на місці — **готівка** або **картка POS** (термінал локації). Еквайринг і ПРРО — окремі системи: гроші йдуть через термінал/касовий ящик, чек формує Checkbox через `FiscalGateway`. Хто позначає: **адмін — для будь-якого візиту**; **барбер — для walk-in** (рекомендація відкритого питання `09` — інакше walk-in ламається операційно; фінальне рішення за засновником, WALK-BAR-03). Решту онлайн-візиту позначає адмін — або клієнт сплачує сам з кабінету (PAY-WEB-01); барбер онлайн-візиту оплату не позначає (PAY-BARBER-01: без сум мережі).
- [ ] **PAY-ONS-02.** Потік позначки: «Оплата на місці» → вибір форми (готівка / картка POS) → сума показана і **не редагується** (`FinalPrice` − депозит; знижки зафіксовані при записі — DSC-001) → підтвердження → `PaymentCaptured` (Payment #2) → статус «Оплачено» (PAY-004). Готівкова здача/розмін — поза системою (касовий облік не ведеться).
- [ ] **PAY-ONS-03.** Чек Checkbox: формується після позначки на суму решти; назва послуги — актуальна з `catalog`, сума — зі снепшоту (PAY-002). Статус чека опитується до `DONE`; затримка `CREATED` / `CANCELLED` / `ERROR` → банер з причиною (зміна не відкрита, зміна > 24 год — обмеження провайдера, README `billing`) і кнопка «Повторити чек»: позначка оплати **не відкочується**, чек доганяється окремо.
- [ ] **PAY-ONS-04.** Ідемпотентність: повторна позначка, подвійний тап, retry не створюють другий `Payment` і другий чек (той самий idempotency-ключ, що PAY-WEB-03; на боці провайдера — наш ID чека, `receipt.already_exists`).
- [ ] **PAY-ONS-05.** Що видно на місці: барбер walk-in і адмін бачать суму до сплати (`FinalPrice` − депозит); депозит і решта — окремо в картці візиту адміна (PAY-ADM-07); факт позначки логується (хто, коли, форма) — видно в «Оплатах» (PAY-ADM-08).

## Admin

- [ ] **PAY-ADM-01.** Статус оплати видно в картці візиту в календарі мережі.
- [ ] **PAY-ADM-02.** Розділ «Оплати»: список `Payment` з фільтрами по локації, даті, статусу; колонки: візит, клієнт, сума, спосіб, статус.
- [ ] **PAY-ADM-03.** Чек Checkbox відкривається і скачується з картки оплати (`FiscalReceipt`).
- [ ] **PAY-ADM-04.** Оплата готівкою: адмін позначає візит «Оплачено (готівка)» вручну; чек формується через Checkbox тим самим флоу.
- [ ] **PAY-ADM-05.** Невдалі оплати (`PaymentFailed`) видно з причиною і часом; по них можна відфільтрувати список.
- [ ] **PAY-ADM-06.** Адмін бачить, які візити очікують депозиту і скільки часу минуло з моменту запису (для нагадувань/deadline депозиту).
- [ ] **PAY-ADM-07.** Решта (70%) на місці: адмін позначає «Решта сплачена на місці» (картка через POS або готівка, PAY-ADM-04); чек Checkbox формується на суму решти; у картці візиту видно депозит і решту окремо.
- [ ] **PAY-ADM-08.** Розділ «Оплати» показує refund-и: сума, `Payment`, причина (своєчасне скасування / зняття no-show), ініціатор (авто/адмін), час, статус повернення; фільтр по статусу.
- [x] **PAY-ADM-09.** **Рішення: вікно скасування — дефолт 4 години, єдине на мережу в v1, налаштовується адміном.** Розділ «Оплати» → «Політика депозита»: % депозита (дефолт 30, 0 = вимкнено), округлення (10 грн), **вікно скасування, год** (дефолт 4). Скоуп: **по локації — override з фази 9** (друга точка: свої ринкові умови); **по барберу — відхилено**: клієнт з «Будь-який барбер» не мусить отримувати різні політики залежно від того, кого призначить система, а депозит захищає крісла мережі, не окремого барбера. Зміни застосовуються **лише до нових записів**: % і вікно снепшотяться на `Appointment` при записі (та сама семантика, що `AgreedPrice`/DSC-001) — скасування оцінюється за снепшотом свого запису, не за поточним налаштуванням; confirm-banner при зміні: «Застосується лише до нових записів».

## Відкриті питання

1. **Прапорець «оплачено» для барбера** (PAY-BARBER-01): за замовчуванням не показувати, поки засновник не вирішить.
2. **Чек клієнту на email**: у v1 — посилання в додатку/кабінеті, email поза scope (`notifications` може додати пізніше).
3. **Повна передоплата**: не в v1 (рішення); може з'явитись як опція пізніше без зміни моделі — але **не як депозит 100%**: ланцюг передоплати Checkbox забороняє платіж = сумі ланцюга (`prepayment.sum_equals_total_sum`, обмеження провайдера — README `billing`). Реалізація — звичайний чек продажу при записі, депозитний флоу не задіяний.
