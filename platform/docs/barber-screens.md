# Екрани барбера (mobile) — walk-in і календар

> Специфікація екранів `apps/mobile` для ролі `barber` (група `(barber)` в Expo Router) — у тому самому стилі, що `admin-screens.md` і `booking-flow.md` (**Layout, Компоненти, Стани, Критерії**). **Документ охоплює**: walk-in флоу (критерії `acceptance-criteria/09-walk-in-booking.md`), календар дня/тижня, картку візиту з референсом зачіски і статуси (критерії `03-appointment-haircut-reference.md`, REF-BARBER-*, `12`, NSH-BAR-01), картку клієнта (§4.3, `MNG-ADM-16`-семантика), self-service графік (§5, `18`). Далі в черзі: відгуки, галерея (§6).
>
> Межі доступу: барбер бачить лише **свої** візити і клієнтів своїх візитів; фінанси мережі — ні (architecture.md). Ціна послуги на картці візиту — операційно потрібна для оплати на місці (WALK-BAR-03).

**Wireframes** — каркас для імплементації: регіони, компоненти, стани; не пікселі (стиль — `references/design-direction.md`). Маркери: `[•]` дія/CTA · `⦿/○` вибір · `[S]` sticky-зона · `⚑` попередження/конфлікт · `⏳` loading · `∅` порожній стан · `↔` порівняння · `FAB` плаваюча кнопка.

## 1. Walk-in: створення живого запису (WALK-BAR-01…03)

### 1.1 Вхід — FAB «Walk-in»

- **Layout**: плаваюча кнопка **«Walk-in»** на календарі дня (§2), виділена кольором, щоб не плутати зі звичайним записом.
- **Стани**: disabled з підказкою «Вільних крісел немає», коли обидва крісла зайняті на поточний час (інваріант 2 крісел).
- **Критерії**: WALK-BAR-01 (вхід), інваріант крісел — фаза 4.

### 1.2 Швидка форма (одна картка, ~10 секунд)

- **Layout**: вертикальний стек полів, фокус на першому полі, без зайвих кроків; кнопка «Створити» внизу.
- **Компоненти (поля)**:
  - **Послуга** — select із активних, доступних у локації; ціна показується поруч (WALK-BAR-03);
  - **Клієнт** — пошук за телефоном (існуючий) АБО «Новий клієнт» → ім'я + телефон (опційно, WALK-003);
  - **Час** — за замовчуванням «Зараз»; можна змінити на найближчий вільний слот;
  - **Коментар** — опційно, ≤ 500 символів.
- **Валідація**: послуга обов'язкова; слот вільний (Availability + OpeningHours + 2 крісла, WALK-002). Для `father-son` — вибір режиму як в онлайн-записі (`PARTY-BAR-03`).
- **Стани**: успіх — візит одразу в календарі з бейджем **«Walk-in»**, активна дія «Почати» (WALK-BAR-02); помилка валідації — повідомлення біля поля.
- **Критерії**: WALK-BAR-01…03, WALK-002/003, `PARTY-BAR-03`.

Wireframe — швидка форма (~10 секунд, одна картка):

```
┌──────────────────────────────┐
│ Walk-in                      │
│ Послуга  [Стрижка · 600 ₴ ▾] │
│ Клієнт   [пошук за телефоном]│
│          або [Новий клієнт]  │
│ Час      Зараз (09:42)       │
│          змінити → слоти     │
│ Коментар [опційно 0/500]     │
│ [Створити]                   │
└──────────────────────────────┘
```

- FAB «Walk-in» живе на календарі дня (§2); disabled при 2/2 зайнятих кріслах з підказкою (інваріант 2 крісел).
- Створений візит — у календарі з бейджем «Walk-in», дія «Почати» активна одразу (WALK-BAR-02); для `father-son` — вибір режиму як в онлайн-записі (`PARTY-BAR-03`).

### 1.3 Оплата на місці (після послуги)

- **Компоненти**: на картці завершеного walk-in — дія **«Оплачено на місці»** (готівка / картка POS) — якщо прийняте рішення, що барбер приймає оплату (відкрите питання `09`); інакше — позначку ставить адмін у веб-адмінці (WALK-ADM-02).
- **Критерії**: чек Checkbox формується через той самий флоу, що PAY-ADM-04/07; механіка позначки — PAY-ONS-01…05 (сума до сплати, ідемпотентність, статус чека); барбер суми мережі не бачить, але суму до сплати своєї послуги бачить (WALK-BAR-03).

## 2. Календар дня

- **Доступ**: перша вкладка нижньої навігації ролі barber. Дані — лише свої візити (`scheduling` за `BarberId`); візити інших барберів не видно (межі — у шапці документа).
- **Layout** (зверху вниз):
  - Заголовок: дата + перемикач «День | Тиждень» (за замовчуванням день) + індикатор «крісла: X/2 зайнято» на поточний час.
  - Таймлайн: вертикальні часові блоки (крок 15 хв) з картками візитів; поточний час — липка лінія. Картка візиту: час, ім'я клієнта, послуга, статус-бейдж (кольори — §4.2).
  - Блок «Очікують підтвердження»: візити в статусі `booked` підсвічуються і збираються нагорі — барбер не мусить шукати їх по таймлайну.
- **Компоненти картки в таймлайні**: мініатюра референсу (якщо є) та іконка коментаря — REF-BARBER-03; статус-бейдж.
- **Взаємодія**: тап на картку → картка візиту (§4); довгий тап → швидкі дії без відкриття (доступні статуси з §4.2); pull-to-refresh + авто-оновлення на фокусі (зміна клієнтом підтягується після синхронізації, REF-BARBER-03).
- **Стани**: порожній — «На цей день записів немає»; вихідний за графіком (§5) — «Вихідний».
- **Критерії**: REF-BARBER-03 (календар), WALK-BAR-01 (FAB), push-оновлення — фаза 7: новий запис / скасування / перенесення оновлюють календар; тап по push відкриває картку візиту.

Wireframe — календар дня:

```
┌──────────────────────────────┐
│ Ср 11.09       День | Тиждень│
│ Крісла: 1/2                  │
│ ОЧІКУЮТЬ ПІДТВЕРДЖЕННЯ (1)   │
│ ┌──────────────────────────┐ │
│ │16:00 Іван · Стрижка  🟡  │ │
│ │[фото] 💬                 │ │
│ └──────────────────────────┘ │
│ 10:00 ────────────────────── │
│ 11:00 ┌──────────────────┐   │
│       │11:00 Марія 🔵    │   │
│       │Гоління           │   │
│       └──────────────────┘   │
│ 14:30 ─── зараз ──────────── │
│ 16:00 (див. вище)            │
│                  [Walk-in]   │ FAB
└──────────────────────────────┘
```

- Блок «Очікують підтвердження» збирає `booked` нагорі; мініатюра референсу і іконка коментаря на картці (REF-BARBER-03); оновлення — pull-to-refresh / на фокусі.
- Тап → картка (§4); довгий тап → швидкі дії статусу (§4.2); FAB disabled при 2/2.
- Порожні стани: «На цей день записів немає» / «Вихідний» (графік §5).

## 3. Календар тижня

- **Layout**: 7 днів (тижневий агрегат: дата, кількість візитів, стисла смуга заповнення годин); поточний день виділений; стрілки ←/→ гортають тижні.
- **Компоненти**: картка дня (дата, «N віз.», смуга заповнення).
- **Взаємодія**: тап на день → календар дня (§2); звідси ж вхід у «Мій графік» (§5).
- **Стани**: ∅ — день без записів; «вих.» — вихідний за графіком (§5); поточний день — виділення рамкою.
- **Правило**: це перегляд, не редактор — зміни графіка лише в §5 (SCH-*).
- **Критерії**: огляд тижня — навігаційний екран; джерело агрегату — ті самі `Appointment` за `BarberId`.

Wireframe — тиждень (огляд, не редактор):

```
┌──────────────────────────────┐
│ ← Вересень 2026 →            │
│ Пн 9    Вт 10   [Ср 11]      │
│ 3 віз.  5 віз.  4 віз.       │
│ ▓▓░░    ▓▓▓░    ▓▓▓▓         │
│ Чт 12   Пт 13   Сб 14   Нд 15│
│ 2 віз.  6 віз.  ∅       вих. │
└──────────────────────────────┘
```

- Тап на день → календар дня (§2); вхід у «Мій графік» (§5); смуга — заповнення годин. Зміни графіка звідси не робляться (SCH-*).

## 4. Картка візиту: референс зачіски, коментар, статуси

Відкривається з календаря (§2/§3) або з push. Одна картка для онлайн-запису і walk-in (walk-in — з бейджем «Walk-in», §1.2).

### 4.1 Референс зачіски і коментар (REF-BARBER-01…05)

- **Layout**: блок під послугою і часом, все разом без кліків (REF-BARBER-01).
- **Компоненти**:
  - **Референс-фото** (AI-варіант або завантажене клієнтом) — прев'ю;
  - **Оригінальне фото клієнта** — поруч, лише коли референс з AI (джерело `haircut-ai`);
  - **Коментар** — звичайний текст ≤ 500 символів, повністю без обрізання (емодзі дозволені, REF-MOB-03).
- **Взаємодія**: тап на будь-яке фото → повноекранний переглядач: дві панелі «Оригінал ↔ Референс» на одному екрані, синхронний зум/пан; кілька референсів — свайп; вихід — жест назад (REF-BARBER-02).
- **Стани**: референс і коментар однакові в календарі (§2) і в картці; після зміни клієнтом — оновлення по синхронізації з API; офлайн — останній відомий стан із міткою «оновлено HH:MM» (REF-BARBER-03). Без референсу — блок не рендериться, без помилок; коментар відсутній — поле не показано (REF-BARBER-04).
- **Перемикач «Опрацьовано»** (REF-BARBER-05, опція, відкрите питання `03`): біля референсу; клієнт бачить, що побажання побачили. Не ввімкнено в v1 — елемент не показується.
- **Критерії**: REF-BARBER-01…05, REF-MOB-03; AI-межі — барбер бачить **лише** вибраний варіант і оригінал, не всі згенеровані (AI-BARBER-01); запуск генерацій і фото поза своїми візитами недоступні (AI-BARBER-02).

Wireframe — картка візиту (стан `booked`, з референсом):

```
┌──────────────────────────────┐
│ ←  16:00 · Іван · Стрижка    │
│ 🟡 Очікує підтвердження      │
│ РЕФЕРЕНС                     │
│ ┌────────┐   ┌────────┐      │
│ │референс│ ↔ │оригінал│ тап  │
│ └────────┘   └────────┘      │
│ 💬 «зняти на 2 мм, чубчик…»  │
│ Іван · +38 0… [📞]           │
│ Оплата: Не оплачено          │
│ [S] [Підтвердити]            │
│     [Позначити no-show]      │
└──────────────────────────────┘
```

- Оригінал — лише для AI-референсу (AI-BARBER-01); без референсу — блок не рендериться (REF-BARBER-04); тап на фото — повноекранне «Оригінал ↔ Референс» (REF-BARBER-02).
- Одна головна кнопка за станом: `booked`→«Підтвердити», `confirmed`→«Почати», `in_progress`→«Завершити»; «Позначити no-show» — вторинна, лише до початку (NSH-BAR-01); «Завершити»/no-show — з діалогом підтвердження.
- Кольори бейджів і події — §4.2; walk-in: бейдж «Walk-in», «Почати» одразу; завершений walk-in — дія «Оплачено на місці» (§1.3). Скасування/перенесення кнопок не мають.

### 4.2 Статуси і дії (життєвий цикл Appointment)

- **Layout**: рядок статусу під шапкою — бейдж + час останньої зміни; зона головної дії — sticky внизу (та сама в усіх станах).
- **Компоненти (кольори бейджів)**: `booked` — жовтий, `confirmed` — синій, `in_progress` — зелений, `completed` — темно-сірий, `no_show` — червоний, `cancelled` — сірий перекреслений.
- **Дії — одна активна головна кнопка**:
  - `booked` → **«Підтвердити»** (депозит сплачений клієнтом) → `confirmed`, подія `AppointmentConfirmed`;
  - `confirmed` → **«Почати»** → `in_progress`; для walk-in — активна одразу після створення (WALK-BAR-02);
  - `in_progress` → **«Завершити»** → `completed`, подія `AppointmentCompleted` (розблоковує відгук і лояльність);
  - `confirmed` до початку → **«Позначити no-show»** — вторинна дія (NSH-BAR-01, без очікування авто-фіксації) → `no_show`, подія `AppointmentNoShowed` (ANL-004).
- **Стани (безпека)**: «Завершити» і «Позначити no-show» — з діалогом підтвердження (дія + клієнт): випадковий тап не фіксує подію, бо події їдуть у KPI і лояльність.
- **Правила**: скасування і перенесення — не дії барбера (клієнт сам або адмін) — кнопки не показуються; статуси не відкочуються (помилка — через адміна в календарі мережі).
- **Партія «батько + син»** (ADR 0011): барбер бачить свої `PartyLeg` — референс/коментар ноги, статуси на нозі; «Завершити» фіксує ногу; `AppointmentPartyCompleted` — коли обидві ноги `complete`; режими sequential/parallel — як у PARTY-BAR-03.
- **Оплата** (WALK-BAR-03 / PAY-BARBER-01): walk-in — дія «Оплачено на місці» (§1.3); онлайн-візит — стан «Оплачено / Не оплачено» без сум і деталей мережі (за прапорцем відкритого питання `01`).
- **Критерії**: REF-BARBER-*, NSH-BAR-01, WALK-BAR-02/03, PAY-BARBER-01, PARTY-BAR-03, ANL-004 (подія для KPI).

### 4.3 Клієнт: короткий блок у візиті і повна картка (MNG-ADM-16-семантика)

- **У картці візиту (компактний блок)**: ім'я, телефон (тап — виклик), коротка примітка з вподобань, якщо є; повна картка — за тапом на блок.
- **Картка клієнта (повна)** — вхід тільки з візитів барбера: барбер бачить лише клієнтів **своїх** візитів (межа доступу в шапці документа).
- **Layout**: шапка (ім'я, телефон, «клієнт з DD.MM.YYYY») → сегменти **«Візити | Вподобання | Нотатки»**.
- **Компоненти**:
  - **Візити**: реверс-хронологічний список минулих візитів цього клієнта у цього барбера (дата, послуга, статус-бейдж); тап → картка того візиту (read-only, §4 без дій). Майбутні візити клієнта в інших барберів не показуються.
  - **Вподобання**: вільний текст з профіля клієнта (алергії, уподобання, «люблю бесіди/тишину») — read-only у барбера; джерело — §5 «Вподобання» у `client-screens.md`, зберігання в `crm` (`MNG-ADM-16`).
  - **Нотатки**: список службових нотаток (дата · автор · текст) + **«Додати нотатку»** (textarea, дата/автор автоматично). Видно барберу і адміну, **не клієнту**; редагування/видалення — лише автора нотатки й адміна.
- **Стани**: порожня історія — «Це перший візит клієнта»; вподобання не заповнені — підказка «Клієнт ще не заповнив вподобання»; нотаток немає — «Нотаток ще немає».
- **Критерії**: `MNG-ADM-16`-семантика для барбера (історія, нотатки, вподобання); межі доступу — шапка документа; нотатки — та сама модель `crm`, що адмінська (§6.2 `admin-screens.md`).

## 5. Мій графік (фаза 22, `SCH-BAR-01…03`)

- **Доступ**: лише з дозволом адміна («Барбер керує графіком сам», SCH-001); без дозволу — режим перегляду з поясненням (`SCH-BAR-03`).
- **Layout**: тижневий редактор (7 рядків Пн…Нд: toggle «Вихідний» або вікна «з–до» + «Додати вікно») → розділ «Вихідні/відпустка» (список діапазонів + «Додати») → «Зберегти» (`SCH-BAR-01`).
- **Валідація**: вікна в межах `OpeningHours` локації (жорстко, SCH-003); без перетинів, макс. 2 вікна/день, крок 15 хв; конфлікти з заброньованими візитами — збереження **блокується**: список конфліктів + «Повідомити адміна» (`SCH-BAR-02`; переносити клієнтів барбер не має права — SCH-004).
- **Стани**: без дозволу — read-only з поясненням; конфлікти — ⚑-блок зі списком візитів.
- **Історія змін**: хто і коли змінив графік (барбер/адмін) — `SCH-BAR-03`.
- **Критерії**: SCH-BAR-01…03, SCH-001/003/004/005; той самий агрегат `Availability`, що адмінський редактор (§2.3 `admin-screens.md`); зміни діють на запис миттєво (SCH-005).

Wireframe — редактор графіка (§5, з дозволом адміна):

```
┌──────────────────────────────┐
│ Мій графік      [Зберегти]   │
│ Пн  [вихідний]               │
│ Вт  09:00–18:00 [+ вікно]    │
│ Ср  09:00–18:00 [+ вікно]    │
│ …                            │
│ Нд  [вихідний]               │
│ ВИХІДНІ / ВІДПУСТКА          │
│ 20.09–27.09        [Видалити]│
│ [+ Додати діапазон]          │
│ ⚑ Конфлікти: 2 візити 12.09  │
│ [Повідомити адміна]          │
│ Історія змін →               │
└──────────────────────────────┘
```

- Вікна: макс. 2/день, крок 15 хв, жорстко в межах `OpeningHours` (SCH-003); конфлікти з заброньованими — збереження блокується, клієнтів переносить лише адмін (SCH-BAR-02, SCH-004).
- Без дозволу адміна — режим перегляду з поясненням (SCH-BAR-03); історія змін — хто/коли (SCH-BAR-03).
