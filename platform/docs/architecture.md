# Архітектура платформи

Платформа — **модульний моноліт з кількома клієнтами**. Одна база, один деплой API, кілька bounded contexts усередині процесу.

Як тримати код у формі, поки його пишуть 27 фаз — [engineering-principles.md](engineering-principles.md): принципи (DDD/SOLID/DRY/KISS/YAGNI), жорсткі обмеження (target LOC < 100 на файл — ADR 0019, складність функції ≤ 10) і піраміда тестів з ковередж-гейтами CI.

## Навіщо так

Мережа: 1 точка зараз, 5–7 за 2–3 роки. Команда: засновник + агенти/підрядники, не окремі команди на сервіс.

Мікросервіси тут зайві: потрібні чіткі межі моделі, а не мережевий розподіл. Контекст можна винести пізніше, якщо навантаження або команда це виправдають.

## C4 — контейнери

```
                    ┌─────────────┐
                    │  iOS / Android │  Expo, ролі client | barber
                    │  apps/mobile   │
                    └──────┬────────┘
                           │ HTTPS + WebSocket
┌─────────────┐     ┌──────▼────────┐     ┌──────────────┐
│  Website    │────▶│  API          │────▶│  PostgreSQL  │
│  apps/web   │     │  apps/api     │     └──────────────┘
│  Next.js    │     │  NestJS       │────▶│  Redis       │
└─────────────┘     └──────▲────────┘     └──────────────┘
                           │
┌─────────────┐            │              ┌──────────────┐
│  Admin      │────────────┘              │  Checkbox    │
│  apps/admin │                           │  еквайринг   │
│  Next.js    │                           │  (ACL)       │

```

Web і admin **не** ходять у БД напряму. Mobile **не** ходить у сторонні CRM. Усі записи, чат і клієнти — через API.

## Шари всередині API

Кожен bounded context:

```
src/{context}/
  domain/            # entity, VO, events, repository port. Нуль фреймворків.
  application/       # use case = транзакція
  infrastructure/    # Prisma, Nest controllers, webhooks, ACL
```

Залежності тільки всередину. Перевірка: доменні тести без БД і HTTP.

Composition root — `apps/api/src/main.ts` (з’явиться в коді): збирає адаптери й віддає їх use cases.

## Поверхні як драйвери

| Драйвер | Адаптер | Що робить |
|---------|---------|-----------|
| Web | HTTP, cookie-сесія клієнта | Публічний контент і блог + кабінет: OTP, записи, профіль |
| Admin | HTTP, cookie/session (інший домен) | Команди мережі, CMS блогу, огляд календаря |
| Mobile | HTTP + WebSocket, bearer | OTP; блог (ті самі статті); барбер: календар, чат |
| Checkbox / еквайринг | webhooks | Підтвердження оплати і чека |
| Scheduler | внутрішня черга Redis | Нагадування, outbox relay |

## Система правди

| Дані | Де правда | Де не правда |
|------|-----------|--------------|
| Візит, слот, статус запису | `scheduling` | Календар Google, нотатки в чаті |
| Картка клієнта, нотатки барбера | `crm` | Identity (там лише логін) |
| Повідомлення | `messaging` | SMS-логи провайдера |
| Стаття блогу | `content` | Копія в додатку, MD-файли в `apps/web` |
| Оплата / фіскальний чек | `billing` + зовнішній провайдер | «Оплачено» в чаті |
| Хто увійшов (сайт і додаток) | `identity` (`PhoneNumber` + сесія) | Ім’я на візитівці, акаунт у Instagram |

Сторонніх CRM і віджетів запису немає (ADR 0001). Нові фічі календаря і чату будуються лише на нашому API.

## Інтеграція між контекстами

- Команда змінює **один** агрегат.
- Побічні ефекти — доменна подія → application handler у іншому контексті.
- Save + publish у одній транзакції через **outbox**, коли подія має доїхати гарантовано (запис → пуш, оплата → статус візиту).

Чернетка імен: [`../packages/contracts/events/README.md`](../packages/contracts/events/README.md).

## Авторизація (грубо)

| Роль | Web | Admin | Mobile |
|------|-----|-------|--------|
| Гість | публічні сторінки, блог, `/login` | ні | блог, екран телефону |
| `client` | кабінет після OTP | ні | той самий акаунт: запис, чат, профіль |
| `barber` | ні | ні | свій календар, свої клієнти, чат |
| `admin` | ні | уся мережа | опційно пізніше, не в v1 |

Клієнтський логін — лише **телефон + OTP** на web і mobile (ADR 0005). Один `UserId` на всіх пристроях.

Барбер не бачить виручку мережі. Клієнт не бачить нотатки барбера. Admin бачить усе, включно з аудитом чату за потреби.

## CORS і браузерні поверхні

Сесія — одна httpOnly cookie на `Domain=.fade.com.ua` (ADR 0017). Браузерні поверхні звертаються до API з іншого origin, тому API віддає CORS **явним allowlist**, не `*`: `*` несумісний із `credentials: true`, без якого cookie не їде.

| Origin | Хто |
|--------|-----|
| `https://fade.com.ua` | публічний сайт, запис (`/booking`, T-053), кабінет (`/account`) |
| `https://admin.fade.com.ua` | адмінка |
| `https://shop.fade.com.ua` | магазин (фаза 27) |
| `http://localhost:13001`, `http://localhost:13002` | dev: web, admin (`.env.example`) |

Правила: `credentials: true`; методи й заголовки — лише потрібні ендпоінтам; mobile (native) CORS не потребує. Джерело allowlist — env `CORS_ALLOWED_ORIGINS`; вмикається, коли в API з'являться HTTP-маршрути (T-001 — каркас без контролерів).

## Що свідомо не робимо зараз

- Окремий BFF на кожну поверхню
- GraphQL
- Event sourcing
- Окремий chat-сервіс (Matrix / Stream) — свій контекст `messaging` достатній
- Окремі додатки «для клієнта» і «для барбера» в сторах — один бінарій, дві ролі
- Пароль або окремий email-акаунт для клієнта — лише телефон + OTP
- Мульти-тенантність як SaaS для чужих мереж — це наша мережа
