# Testing guidelines — як ми тестуємо

> **Статус:** реальний мінімум, верифікований по фактичному коду (2026-09-24). Не фантом.
> **Зв'язки:** [engineering-principles.md](engineering-principles.md) — філософія піраміди, ковередж-гейти, правила якості тестів. Цей документ — **конкретні конвенції «як саме»**: імена, конфіги, double'и, e2e-шари. Розширюється під час першої задачі, що його чіпає.

## 1. Конвенції файлів і запуск

| Що | Де | Суфікс | Запуск |
|----|----|--------|--------|
| Unit/functional (API) | колокований `*.spec.ts` поруч із кодом | `.spec.ts` | `pnpm --filter api test` |
| API e2e (модуль + HTTP; більшість — на фейках) | `src/<context>/e2e/*.e2e.spec.ts` | `.e2e.spec.ts` | `pnpm --filter api test:functional` |
| API e2e з реальним PrismaService | там само | `.e2e.spec.ts` | те саме, але БД ізольована: `barbershop_e2e` (§1.2) |
| Web-тести | колоковані `*.test.ts` | `.test.ts` | `pnpm --filter web test` |
| Playwright (web) | `apps/web/e2e/*.spec.ts` | `.spec.ts` | `pnpm e2e` (з кореня; очікує живі :3001 + :13000) |
| Playwright (admin, §6.2 телефонний запис) | `apps/admin/e2e/*.spec.ts` | `.spec.ts` | `pnpm e2e:admin` (з кореня; очікує живі :13002 + :13000 + smspit :19096) |

- Обидва jest-пресети: `ts-jest`, корінь `src/`, матчинг `**/?(*.)+(spec|test).ts`.
- **`.e2e.spec.ts` ≠ `.e2e-spec.ts`** — суфікс із дефісом не матчується конфігом (перевірено болісно).

### 1.1 Playwright адмінки: OTP через Mailpit (§6.2, T-4409/T-046)

`apps/admin/e2e/phone-booking.spec.ts` — димовий прогін екрана телефонного запису наскрізь: логін адміна → «Надіслати код» → **справжній** OTP із Mailpit (`GET /api/v1/messages` + `/api/v1/message/:id`, T-4301 «SMSPitt») → форма візиту → 201 → перевірка, що в `/admin/calendar` візит має непорожній `clientId`.

- **Перекриття.** Клієнт (`E2E_CLIENT_PHONE`, дефолт `+380501112233`) і барбер (`E2E_BARBER_NAME`, дефолт `Oleh`) — із сіду. Номер **не** довільний: verify відкидає невідомого користувача як `USER_NOT_FOUND`. Барбер — саме з сіду: у спільній dev-БД живуть барбери-фікстури-e2e без `AvailabilityWindow`, і POST відповідає їм `400 Barber has no availability for this slot`.
- **Знімок Mailpit перед надсиланням** (`snapshotBookingOtpIds`). Mailpit персистентний, тож без знімка тест читає код попереднього прогону — він і є «найновішим», поки новий не доставлено, — і отримує `OTP_INVALID`.
- **Слот.** День Пн–Сб (неділя закрита), початок на **15-хв сітці** (`09:45` проходить, `09:46` → 400), крок рухається щокроково, щоб не впитися в `409 No free chairs` (у локації рівно 2 крісла).
- **Лімітери — не обійти, а пояснити.** Повторна відправка OTP має кулдаун `OTP_RESEND_SEC = 60`, а логін адміна — Redis-ключ `ratelimit:admin-login:*`. Тест падає з текстом помилки відразу, а не чекає на код, який не прийде; між локальними прогонами потрібна пауза.
- **Локатор помилок** — `section[aria-label="Верифікація номера"] p[role="alert"]`, а не `getByRole('alert')`: на сторінці завжди є порожній alert-вузол-обгортка, тож роль-локатор збігається навіть коли помилки немає. Так само логін перевіряється позитивно («Вийти»), бо «Увійти» зникає й під час завантаження.
- **Не в CI.** `ci.yml` не має Playwright-job (ні для web, ні для admin) — сценарий потребує живого стеку; це команда рівня `pnpm e2e`, а не гейт.

### 1.2 Ізоляція БД для e2e (обовʼязково)

П'ять сюїт використовують **реальний** `PrismaService` (решта підміняє його фейком): `appointment-lifecycle`, `appointment-party-race`, `booking-flow-gwt`, `client-booking-confirm`, `admin-bookings`. Вони пишуть реальні рядки — і раніше писали їх у **спільну dev-БД**. Наслідок був неочевидним: фікстури («LC Barber») зʼявлялися в адмінських dropdown'ах, займали крісла й слоти, аж поки чистий сід переставав бути чистим.

- **Окрема база `barbershop_e2e`**, не схема на воркер: Prisma застосовує міграції до конкретної схеми, тож для схем-на-воркер довелося б ганяти `migrate deploy` N разів (maxWorkers 35% на multicore). Одна база = один прогін міграцій.
- **Хто перемикає.** `pretest:functional` → `node scripts/e2e-db.cjs prepare` (створити базу + `prisma migrate deploy`, ідемпотентно), а `test:functional` запускає jest із `FADE_E2E_ISOLATED=1`, і `jest.setup.js` підміняє `DATABASE_URL` на похідний від базового з іншим іменем бази.
- **Запобіжник.** `assertIsolated()` **падає**, якщо цільова база збігається з базовою. Тихий фолбек на dev знову дав би змішування без видимої причини — це гірше за явну помилку.
- **Юніти не зачіплені.** `test:unit` не ставить прапорець і лишається на dev-URL; юніт-тести й так працюють на фейках (`makeSeedPrisma()`), тож БД не чіпають.
- **Перевірка, що ізоляція жива:** прогін `test:functional`, потім порівняти лічильники в dev-БД — вони мають бути **незмінними**.
- **Playwright не ізольовано.** `pnpm e2e` і `pnpm e2e:admin` ходять у живий стек, тобто в dev-БД. Повна ізоляція потребує окремого стеку — це окрема задача, не ця.

#### 1.2a `fresh-bootstrap` працює лише в одноразовому compose-проєкті

`apps/api/src/e2e/fresh-bootstrap.e2e.spec.ts` доводить, що **чиста** база піднімається з нуля: `prisma migrate reset` застосовує всі міграції по порядку, а сід створює CRM-профіль кожному клієнту. Для цього йому потрібен `down -v`, тобто знищення тому з даними, — тому на робочому стеку розробника він не запускається **ніколи**.

- **Окремий проєкт, а не «обережно з тим самим».** `-p fade-fresh-bootstrap` дає власні томи (`fade-fresh-bootstrap_pg_data`), а `infra/docker-compose.fresh-bootstrap.yml` розводить те, що `-p` не розводить: явні `container_name`, ім'я мережі й хост-порти (`25432` постгрес, `26379` redis, `29000/29001` minio).
- **`!override` для портів.** Compose зливає списки додаванням, тож звичайний `ports:` лишив би в контейнері **обидва** мапінги — і базовий `15432`, і одноразовий; свіжий postgres падав би на «port is already allocated» поруч із робочим.
- **`--profile` потрібен і для `down`.** Без нього compose не бачить сервісів із вимкнених профілів, вважає стек порожнім і мовчки виходить з кодом 0, лишаючи контейнери й томи жити. Тому `--profile` стоїть у спільному префіксі кожного виклику, а не лише в `up`.
- **Сід пише в одноразову базу.** `runSeedE2e` передає `DATABASE_URL`, побудований з порту цього ж проєкту; без цього `prisma migrate reset` пішов би в ту базу, на яку дивиться оболонка розробника.
- **Запобіжник.** `fresh-bootstrap.docker.ts` падає, якщо підсумковий проєкт збігається з робочим `fade-platform`.
- **Профілі.** Типово піднімаються лише `deps` (postgres, redis, minio) — твердження сюїти про базу і сід, а контейнерам застосунків потрібна холодна інсталяція `node_modules` у свій том. Повний стек: `FADE_FRESH_BOOTSTRAP_PROFILES=deps,apps`.
- **Перевірка, що ізоляція жива:** до і після прогону порівняти `docker ps --filter name=fade-platform` і лічильники в dev-БД; вони мають бути незмінними, а після `afterAll` у проєкті `fade-fresh-bootstrap` не має лишитися ні контейнерів, ні томів, ні мережі.
- **Не в банді `test:functional`.** Сюїта виключена з нього явно (`--testPathIgnorePatterns='/node_modules/|fresh-bootstrap'`): вона вимагає Docker, знищує томи й додає хвилину, а банд іде із `--forceExit` на спільній e2e-базі. Запуск — точковий: `npx jest src/e2e/fresh-bootstrap.e2e.spec.ts` з `apps/api`.

### 1.3 Спільні унікальні значення в e2e-фікстурах (обов'язково)

Спільна e2e-БД означає, що **фіксований унікальний рядок робить сюїти залежними від порядку**. `Session.tokenHash` — `@unique`, тож `seedWebClient(prisma, id, 'web-reschedule-token')` ламає кожен паралельний прогін: другий insert → P2002, а guard вже встигає підставити сесію іншого користувача → **401 замість очікуваного 200**. Те саме з location `code`, `phone` і будь-яким іншим `@unique`.

- **Токен/код — із `randomUUID()` на кожен прогін**, не константа модуля. Константа lived у `reschedule-chain` і роняла сусідні сюїти того самого воркера.
- **`useValue` із preseeded-інстансом, а не `useClass`** (див. §2) — інакше DI створює власний пустй інстанс.

### 1.4 Ледж-фікстура в Suite: не лишати частковий стенд

`syncBefore`-bootstrap, який впав у `beforeAll`, робив дві речі: (1) `afterAll(() => ctx.cleanup())` падав із `Cannot read properties of undefined`, **маскуючи справжню помилку**; (2) Nest app і пул Prisma лишалися відкритими в воркері, а наступні сюїти отримували `socket hang up`. Тому `lifecycleSuite` тепер обгортає bootstrap у `try/catch`, закриває те, що вже піднято, і **повторно кидає** оригінальну помилку — а `cleanup` є функцією-замикачем, безпечною до виклику.

### 1.5 Не импортувати `AppModule` в e2e

`admin-clients` був єдиною сюїтою з `imports: [AppModule]` — тобто з **реальним** `PrismaService`, Redis-геокодером і пулом з'єднань серед сюїт, які свідомо in-memory. На паралельному прогоні це давало сусіднім сюїтам `503` і `socket hang up`. Імпортувати треба лише `CrmModule` + `IdentityModule` (остання — заради глобального `AdminSessionGuard`, а не заради репозиторіїв: вони підміняються). Загальне правило: e2e піднімає **модуль свого контексту**, а не застосунку.

### 1.6 Не «лікувати» флейк підняттям таймаутів

Спокуса — поставити `testTimeout` і назвати флейк нестабільністю CI. Виміряно: підняття до 30 с дало `Exceeded timeout of 30000 ms` на швидких in-memory сюїтах, тобто проблема була **в нестачі CPU, а не в замалому ліміті**; довший таймаут лише тримає воркер і пул зайнятими довше й підсилює конкуренцію. Лікувати треба причину (спільні унікальні значення, невісіданий стенд, важкий імпорт), а не час.

## 2. API-тести: шари double'ів

1. **Домен/application** — жодних БД/HTTP; час і id — ін'єктовані (`Clock`, `IdGenerator`), ACL-порти — фейки з `ports.fakes.ts` (`FakeGeocoder`, `FakeOutbox`).
2. **Infrastructure** — юнит-тести тільки для чистої логіки адаптерів (кеш/ліміти, нормалізація). Транзакційні адаптери покриваються e2e (коментар у jest-конфігу).
3. **API e2e** — `Test.createTestingModule({ imports: [RealModule] })` + `overrideProvider`:
   - `PrismaService` → об'єкт із `$connect/$disconnect/$transaction` + мінімальні model-методи; краще — перевизначати **репозиторій-адаптер** in-memory реалізацією на рівні **доменних агрегатів** (патерн `locations.e2e.spec.ts`);
   - зовнішні ACL-адаптери (геокодер, OTP-відправник) — стаби за маркер-токенами (`CACHED_ROUTING_GEOCODER`);
   - `useValue` з попередньо заповненим інстансом — **не** `useClass` (той створює порожній інстанс і викидає ваші дані — перевірено болісно).
4. **Playwright** — геолокація підмінюється `grantPermissions('geolocation') + setGeolocation`; сервери зовнішні (див. шапку `playwright.config.ts`). Твердження про порядок — на радіус-логіці use case, не на зовнішніх сервісах (Nominatim) — детермінізм.

## 3. Дані, твердження, стабільність

- Тест-дані збираються **під сценарій** (house-хелпери `createLocation`, `test-helpers.fakes`); спільні «на все» фікстури заборонені (engineering-principles).
- **Дата-залежність = баг.** Очікування від реального годинника (наприклад, день-ключ логера) виводиться в тесті з того самого годинника; для логіки «між днями» — ін'єктований годинник. Кожна дата-фрагільна специфікація — це баг у дизайн залежностей, фікс на місці.
- Асинхронна файлова система/потоки: чекати завершення (`await close()` перед читанням файлу) — `createWriteStream` відкриває файл асинхронно.
- `noUncheckedIndexedAccess` у базовому tsconfig: елементи масивів за індексом — `arr[0]!` (house-стиль) або `?? default` — компілятор не пропускає `string | undefined` у `string`.
- Очікування помилок — за класом домену (`ServiceCodeTakenError`), не за текстом.

## 4. Ковередж і гейти (нагадування; повна таблиця — engineering-principles)

- API: ≥ 85% lines / ≥ 80% branches глобально; **domain та application — ≥ 90%**; інфраструктура виключена з coverage (покривається e2e).
- Новий файл без тестів — не рев'ю; flaky-тест чиниться або видаляється у тому ж спринті.
- Документи й схеми теж мають гейт: `pnpm docs:validate` (цитати ADR/docs, DoD↔roadmap, traceability) — червоний білд валить PR так само, як юнит-тест.
