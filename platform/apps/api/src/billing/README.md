# Оплата та фіскалізація (`billing`)

> Тип піддомену: **Generic (ACL)**

Платежі та чеки. Зовнішні системи (еквайринг, Checkbox) ховаються за anti-corruption layer.

## Ubiquitous language

- **Payment** — оплата візиту або депозиту.
- **FiscalReceipt** — фіскальний чек ПРРО.
- **PaymentMethod** — форма оплати: картка, готівка, подарунковий сертифікат (ADR 0013). Один чек може містити кілька форм оплати (сертифікат частково + картка/готівка — GFT-003).
- **PaymentByParts** — оплата `FinalPrice` частинами різними формами: депозит+решта (PAY-001) або сертифікат+решта.
- **ComplimentaryVisit** — візит з `FinalPrice = 0`; причина фіксується поза `billing` (`loyalty` — LYL-ADM-05, `full_discount_promo` — DSC-ADM-07). Не є платіжною подією — див. інваріант у «Domain events».
- **CancellationPolicy** — політика скасування депозита: % депозита, округлення, **вікно скасування** (год; дефолт 4, PAY-ADM-09). Єдина на мережу в v1 (override по локації — з фази 9); снепшотиться на `Appointment` при записі — скасування оцінюється за снепшотом свого запису.

## Domain events (план)

- `PaymentInitiated`
- `PaymentCaptured`
- `ReceiptIssued`
- `PaymentFailed`
- `PaymentRefunded` (повернення депозита: скасування за ≥ вікно `CancellationPolicy` (дефолт 4 год) — автоматично через `AcquiringGateway` без ручних дій, зняття no-show — вручну адміном (NSH-ADM-03); рівно один на `Payment`, ідемпотентність і гонки скасування/no-show — PAY-005…010; стани `captured → refunding → refunded | refund_failed`; супроводжується видатковим чеком на суму повернення з `related_receipt_id` на чек депозита)

**Інваріант (PAY-003, LYL-007): безоплатний візит не генерує платіжних подій.** При `FinalPrice = 0` (ComplimentaryVisit — незалежно від причини нуля: лояльність або 100% промокод, DSC-013):

- жодного `Payment` → **ні `PaymentInitiated`, ні `PaymentCaptured`, ні `PaymentFailed`**;
- жодного виклику `FiscalGateway` (Checkbox) → **ні `ReceiptIssued`**: безоплатне надання не є розрахунковою операцією, депозит = 30% × 0 = 0 не стягується;
- `PaymentRefunded` на такому візиті неможливий за побудовою — refund-ати нічого.

Імплементація: guard за **сумою** (`FinalPrice = 0`) в use case ініціації оплати і в депозитному флоу, не за причиною нуля — будь-який майбутній механізм з нулем на виході успадковує інваріант автоматично. Візит залишається в обліку (`scheduling`/`crm`) і доступний адмін-звітам як 0-грн запис з причиною (LYL-ADM-05, DSC-ADM-07) — read-модель, не `Payment`.

## Провайдер: верифіковані обмеження Checkbox (API, 2026-09-11)

Перевірено проти специфікації WebAPI (`wiki.checkbox.ua/api`). Що це фіксує для нашого флоу:

1. **Розділ чеків підтримується нативно** — не двома незалежними продажами, а ланцюгом **передоплата/післяплата**: депозит → чек передплати (аванс), решта → закриваючий чек ланцюга. Обидва чеки ланцюга — **на касі одного типу** (`cash_register_identity`) → депозит і решта одного візиту йдуть через касу локації (наша модель «каса на локацію»).
2. **Обмеження ланцюга**: сума чека передплати не може дорівнювати сумі всього ланцюга (`prepayment.sum_equals_total_sum`) → **депозит 100% неможливий як ланцюг**; повна передоплата (якщо колись ввімкнуть) = звичайний чек продажу при записі, не депозит (уточнює відкрите питання `01`). Депозит 30% — валідний (< 100%).
3. **Повернення = видатковий чек** з `related_receipt_id` на оригінал; повернення ланцюга передоплати — через механізм ланцюга (`receipt.return_prepayment` забороняє повертати чек передоплати як звичайний; `prepayment.already_returned` = ланцюг уже повернуто). Повне повернення депозита = повернення ланцюга — узгоджується з PAY-005/006 (лише повна сума, один refund на `Payment`). Provider-стороння ідемпотентність доповнює нашу: `receipt.goods_already_returned`.
4. **Готівкові повернення обмежені**: брак готівки в касі (`receipt.not_enough_balance`) і денні ліміти на готівкове повернення передоплат (`prepayment.daily_limit_return`) → refund готівкою на місці може бути фізично неможливий у момент; для нас refund клієнту йде **на картку** (еквайринг), готівкові refund-и — ручна операція адміна з цими обмеженнями на увазі.
5. **Скасування останнього чека** (`reject_last_receipt.*`) — лише останній чек **поточної відкритої зміни**, не для передоплати → це інструмент для миттєвих помилок касира, **не** механізм refund-ів (наші refund-и пізніше — завжди видаткові чеки).
6. **Статуси чека**: `CREATED → DONE | CANCELLED | ERROR`; візуалізація — лише після `DONE`. Подія `ReceiptIssued` у нас фіксується **на `DONE`**, не на створенні; статус чека опитується через API (webhook-и в Checkbox існують, але ми на них не покладаємось).
7. **Ідемпотентність на нашому боці передається провайдеру**: **ID чека, який генерує інтеграція** (`receipt.already_exists` при дублі) і `custom_relation_id` ланцюга (`prepayment.relation_id_not_unique`) → передаємо наш `PaymentId` / ключ на основі `AppointmentId` (PAY-WEB-03, PAY-006).
8. **Нуль і округлення**: платіж, що після округлення дорівнює 0, не приймається (`receipt.zero_payment_after_rounding`); нульові платежі в запиті обмежені (`receipt.zero_payments`) → якщо депозит, округлений до 10 грн, дає 0 — чек не створюється (конфіг поводиться як «вимкнено»); `FinalPrice = 0` до Checkbox ніколи не доходить (PAY-003, ComplimentaryVisit).
9. **Зміни**: чек можливий лише у відкритій зміні (`shift.not_opened`); зміна, відкрита > 24 год, блокує фіскальні дії (`shift.opened_too_long`) → перед чеком перевіряти зміну, помилку показувати адміну; операційно — закривати зміну щодня (Z-звіт), інакше ранкова зміна заблокує перший депозит.
10. **Тестове середовище**: той самий хост, тестові каса/касир; ліміт **100 чеків/міс на тестову касу**; тестові чеки повертаються лише з тієї ж тестової каси (`receipt.test_cash_register`) → тестовий чек у чеклисті запуску робити з запасом ліміту і на тій самій касі, що й повернення.
11. **Форми оплати**: у потоках специфікації — готівка/картка; **сертифікат як форма оплати** специфікацією явно не покривається — залишається під прапорцем перевірки ADR 0013 (при інтеграції з Checkbox).

Висновок: модель PAY-001…008 (0–2 `Payment` на візит, чек на кожен, ідемпотентність, повний refund депозита) реалізується без змін; уточнення — пункт 2 (100% депозит) і пункт 8 (нуль після округлення).

## Хто викликає

Admin, mobile (статус оплати), Checkbox webhook → API.

- `gift-certificates` (ADR 0013): **продаж** сертифіката — команда на прийом платежу і чек #1 («Подарунковий сертифікат»); **погашення** — списання балансу відбувається у `gift-certificates`, `billing` проводить чек #2 на `FinalPrice` із сертифікатом як формою оплати. Сертифікат не створює `Payment` — це списання з контексту-власника, не транзакція еквайрингу.

## Шарність

- `domain/` — Чиста модель. Без Nest, Prisma, HTTP, Expo. Тут entities, value objects, events, repository-порти.
- `application/` — Use cases: command/query, handlers, політики доступу. Транзакція = один use case.
- `infrastructure/` — Адаптери цього контексту (Prisma, HTTP, черга). Зовнішні системи лише через ACL, не в domain.

Код домену не імпортує Nest, Prisma, React Native і HTTP-клієнти. Залежності спрямовані всередину: infrastructure → application → domain.

Публічний API контексту (коли з’явиться код) реекспортує domain + application, **не** infrastructure.
